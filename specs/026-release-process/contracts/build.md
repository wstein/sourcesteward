# Contract: `stw release build`

## Command

```text
stw release build --mode ci       --commit C --version V [--product NAME] --out DIR [--files-only] [--json]
stw release build --mode ci       --smoke TARGET --commit C --version V [--product NAME] --out DIR [--json]
stw release build --mode promote  --tag T [--product NAME] --record FILE [--json]
stw release build --mode local-verify --commit C --version V [--product NAME] --record FILE [--json]
```

`build` is the only command that executes project commands. It exists so the workflow runs one audited code path instead of shell glue. It is refused by default.

| Mode | When allowed | Effect |
| --- | --- | --- |
| `ci` | `GITHUB_ACTIONS=true`; the checkout was made with full history (the workflow uses `fetch-depth: 0`), HEAD equals C, tracked tree clean (`git diff-index --quiet HEAD`); the contract at C passes `check`; the offline build gates are re-evaluated and any `fail` or `not-run` refuses `gate-failed` (a shallow checkout therefore refuses) (the online gates were evaluated by the preceding workflow step); `--out DIR` is new and empty | executes each `[[build]]` as the spec's [build table](../spec.md#build-environment-normative) says (compile builds and `fetch` builds alike), collects declared outputs into `DIR`, writes `SHA256SUMS` and `build-manifest.json` there. `--files-only` skips `oci-image` targets, their per-target invocations and builds used only by images (the reproducibility workflow must not push images). Before any project invocation it refuses `unsupported-target` if a `scope = "once"` build is shared by file and image targets: files-only requires separate file/image once builds. The same mixed once build remains valid without `--files-only` |
| `ci --smoke TARGET` | as `ci`, with `--out DIR` an existing directory holding the build outputs (read only) | runs the target's `smoke_argv` with the working directory at the root of the checked-out commit C, with `{artifact}` the absolute path of the target's output file in `DIR`; `stw` does not extract anything, the project's smoke script does; exit status of the command is the result |
| `promote` | `GITHUB_ACTIONS=true`, the workflow's verification step passed in the same run (the workflow orders the steps), `FILE` is the record read from the tag commit or the record commit | for each `oci-image` asset of the record executes `[promote].argv` with `{repository}`, `{digest}`, `{version}` and `{version_number}` (the promote row of the placeholder table) taken from the record under the same environment rules; it adds the version tag to the same digest and never rebuilds, pushes a new image or changes another tag; if the tag already points to that digest it succeeds without change, and if it points to another digest it refuses (`promote-failed`) |
| `local-verify` | explicit user authorization in the caller's task context for a verification rebuild; Git-owned checkout; the selected product's trusted contract at C has file targets exclusively | exports C's tree from tree objects into a fresh temporary directory (regular files, modes 0644/0755, `O_EXCL`, symlinks, gitlinks, `.git`, `..`, absolute, duplicate or case-colliding names and grafts refused with `export-unsafe`), builds there with the same environment, compares each artifact hash with `FILE` (a record or a build manifest) and prints the comparison; output stays in a temporary directory that is removed; nothing is published, pushed, tagged or registry-tagged |

`local-verify` is a scoped file-only capability. If the selected trusted contract contains any `oci-image` target, including a mixed file/image product, it refuses `unsupported-target` (exit 1) before tree export, project command execution or network. The contract determines this check: omitting OCI assets from the comparison record or manifest cannot bypass it, and `--files-only` does not turn an OCI/mixed product into an eligible local verification. OCI building in `ci` and digest-only `promote` remain supported with their existing effects. Local OCI verification is deferred; no equivalent local image reproducibility claim is made.

Neither `ci` nor `local-verify` changes refs, the index or the working tree of the user's checkout (in `ci` mode the checkout is the CI's own). Any other mode, or `ci`/`promote` outside GitHub Actions, refuses with `ci-only`; `local-verify` without `--record` is a usage error. `local-verify` is **not** the release build and its output is never uploaded; it answers "does a second build of C give the recorded hashes" for the owner. A fetch build reaches its declared hosts; `local-verify` of a fetch build therefore needs the same network and the owner's authorization states that.

## Checkout comparison view (`ci`, `ci --smoke`)

The "tracked tree clean" predicate is not evaluated against the live checkout metadata. Before the first project invocation `stw` freezes a private view of it: descriptor-relative, no-follow capture of the `.git` anchor, git directory, common directory, index (including a split-index base) and every configuration source, rendered into one flat private native configuration, for the checkout and for each initialized gitlink checkout, in a 0700 directory owned by the process and removed on every path. The native comparison (`git diff-index --quiet --no-ext-diff --no-textconv C --`) runs with a minimal environment (no project secrets, no inherited `GIT_*`, no hooks, no fsmonitor, no optional locks), as a supervised process group that is `SIGKILL`ed as a whole and is released only after it and its output streams ended. A nested `git status` of a gitlink checkout is routed to `stw` itself (argv0 `git` with a private role variable, handled before command parsing in `cmd/stw`), so it cannot refresh the source index. After the last project invocation the bindings, the captured configuration, HEAD and the comparison are revalidated: a change of any bound metadata or of the native configuration during the build is refused as `checkout-mismatch`, in addition to a tracked-tree difference. `promote` does not use the view: it runs the declared image-tag command against a validated record and compares no checkout. The index is the one bound input that a project step may legitimately rewrite (a stat refresh by `git status` or `git describe --dirty`), so it is compared by meaning, not by bytes or inode: each entry's mode, object, stage and path plus the assume-unchanged, skip-worktree and intent-to-add flags must equal the capture, and the tracked-tree comparison runs on a verified copy of the live index. Before the comparison the stat data (ctime, mtime, device, inode, size) of every entry in that copy is cleared, a split index is folded into one file first, and native `git update-index --refresh` re-hashes every tracked file, so an mtime, size or inode forged in the live index is never trusted. Still not verified: entries flagged assume-unchanged or skip-worktree are bound by their flag but, as in Git itself, their worktree content is not re-read, and the worktree content of a gitlink checkout is bound only through its index entries, not compared with the requested commit. A checkout that uses a sparse index (`index.sparse`) is refused, with a message that names it, because native Git expands the index and reports that on its diagnostic stream; a cone-mode sparse checkout with a full index is accepted. The private directory itself is sealed after preparation (digest of every file, link target of every symlink) and verified before each comparison; a process of the same user can still replace a private file between two verifications and restore it, which the 0700 directory does not prevent. Not frozen: attributes are read by native Git at comparison time from the worktree `.gitattributes` files, the live `info/attributes` of the common directory (reached through a link, not copied) and the user-level attributes file selected by the inherited `HOME` and `XDG_CONFIG_HOME`; system attributes are disabled, and configured conversion helpers are refused by a separate screen before and after the build. The view adds no mode, flag or refusal code. The specification previously named only the predicate (`git diff-index --quiet HEAD`) and the refusal; this section records the isolation chosen for it (owner review pending).

## Procedure (`ci`)

1. Validate version against the scheme; read the contract at C from the tree; compute `config_sha256`.
2. Before any project invocation, `--files-only` checks every once build against all targets of the trusted contract and refuses a shared file/image build (`unsupported-target`). Filtering collection cannot suppress the declared image-producing effects of that unchanged once invocation. Per-target image invocations and image-only builds are omitted. For each remaining build in file order, for each invocation (per-target: each referencing target; once: one): construct the environment and argv by substitution, run with `timeout_seconds`, bounded output (1 MiB per stream retained, the rest discarded with a note), process group killed on timeout or cancellation. Exit status != 0 stops the build (`status: error`, code `build-failed`, the failing build id).
3. Verify each declared `output` exists as a regular file under `dist/release/`; read each `result_file` against its schema (`oci-image`); reject extra files only by reporting them (`unexpected-output` info).
4. Copy outputs into `DIR`, compute hashes and sizes, write `SHA256SUMS` (`sha256sum -c` format, sorted by name) and `build-manifest.json` (canonical form).
5. Smoke (`--smoke TARGET`) is a separate invocation on the target's native runner; the runner obtains the `stw` binary from the workflow's hand-off artifact ([workflow contract](workflow.md)).
6. The build manifest records, for every build, `network`, `network_hosts` and the SHA-256 of each `lock_files` entry read from C's tree, so a fetch is disclosed in the attested document.

## Exit status

0 built or promoted; 1 refusal or operational failure (`ci-only`, `build-failed`, `promote-failed`, `checkout-mismatch`, `gate-failed`, `output-exists`, `export-unsafe`, `unsupported-target`, `canceled`, `release-limit`); 2 usage; 3 `local-verify` found a hash difference (`artifact-mismatch`). Precedence 2, 1, 3, 0.

## Backend capability

`ci`: the workflow's checkout is Git; `build` refuses a jj-owned or ambiguous tree. `local-verify`: Git only and file-only products; jj and GitButler refuse with `unsupported-backend`, while OCI/mixed products in Git refuse with `unsupported-target` before export or execution.

## Effects

Executes project commands (disclosed, the purpose). A `fetch` build contacts its declared hosts; `stw` does not enforce or sandbox that. Writes: `DIR` (new, empty), the project's own build outputs, and the temporary export in `local-verify`. Network: whatever the project command does; `stw` itself makes none. Secrets: `stw` passes none and constructs the environment (an inherited `HOME` can still expose files of the runner user; the runner is ephemeral). Not done: tagging, pushing, publishing, registry tagging, promoting, attesting (the workflow's attest action does that).

## Compatibility

New command. It is the one command whose effects the constitution amendment proposal names.
