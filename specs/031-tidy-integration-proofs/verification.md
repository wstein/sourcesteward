Decisions and findings of this package (no requirement or contract was changed; the additive items are open questions for the owner):

- The journal carries no clock: "journal time" is the modification time of the journal record, which every journal transition refreshes (its last change is the end of the apply).
- `--as` is accepted by the read-only plan as well as by the apply, so a name can be checked before it is used (the contract's usage rules do not restrict it to apply).
- The plan reads references and commits in batches: one `for-each-ref` with exact patterns per 100 names (the exact name sorts first and only exact matches are used) and one `cat-file --batch-check` for all `OID^{commit}` lines, instead of one `symbolic-ref` and one `cat-file -e` per entry; the observable states and reasons are those of the contract. Git's `for-each-ref` skips a dangling symbolic ref, so the plan cannot see a dangling symbolic target; the apply re-evaluation asks `git symbolic-ref -q` for that entry and the compare-and-swap refuses anyway, so such a target ends as `symbolic-reference` without a record or effect.
- The hook refusal reuses the strict Spec 029 apply admission (`gitSafety` without the planning neutralization): it refuses configured and default hooks, `core.hooksPath`, `core.fsmonitor`, submodule configuration and the same tree conditions as `tidy apply`, so a repository `tidy apply` cannot work in cannot be restored into by `restore --apply` either. The plan has no such condition.
- A journal whose phase is unknown fails the existing journal validation and is `journal-unreadable` (a refusal), not a per-entry `journal-incomplete`; per-entry `journal-incomplete` covers entries without a confirmed recovery and invalid ref names.
- A restore apply has a five-minute deadline (a plan 60 seconds), because it spends about four native processes per entry and up to 1,024 entries exist; a deadline leaves the remaining entries `not-attempted` and a rerun continues. The Spec 029 deadline of 60 seconds does not apply to this new command.
- History truncation markers use the units `journals` (the limit or the scan cap), `objects` (the 65,536-line input bound or the 4 MiB output bound) and `checked-journals` (the 30-second budget). `restore --list` reports `tidy-restore` as its command name, `tidy history` `tidy-history`. `retained` counts plan candidates that were not selected for deletion, `deleted` the journal entries that finished, and the decision kinds count the journal entries' decisions.
- The restore journal names its records by a hash of plan and action and a sequence number because both identities can be 128 bytes long; the `restore_journal` field of an entry holds the intent and outcome record identities written by that apply.
