# Feature Specification: Tidy git-native integration proofs, PR discovery and bounded planning

**Branch**: `codex/spec-tidy-integration-proofs` | **Created**: 2026-10-19
**Status**: Draft specification; no runtime implementation. Requires independent review before tasks start.
**Input**: Dogfooding `stw tidy` (Spec 029 contract 3) on this repository (149 local branches, 111 worktrees, GitHub rebase-merge) and on the Anchorage umbrella (submodules). Forge issues: #79 (plan refused for `submodule.*` or `core.hooksPath` configuration), #80 (v1 plan fails at the 64 KiB `nativeOutputLimit` around 146 branches/86 worktrees), #81 (v3 online plan needs explicit `--pr OID=N`; duplicate OIDs rejected as duplicate hints; offline rebase-merge integration is not detected: 93 of 149 refs `integration-not-proven`).

## Scope and decision status

This Spec **amends** Spec 029 (local tidy with explicit integration evidence) where stated in [its contract amendments](../029-tidy-dogfood-safety/contract-amendments.md#spec-031-amendments): Spec 029 treats patch similarity as optional supporting information only; this Spec makes forge-free patch equivalence (`patch-exact`, `patch-id`), `merge-noop` and `no-net-change` default deletion classes with exact semantics and a whitespace-significance guard, because local deletion is recoverable. Spec 029 otherwise remains the owner of contract 3 commands, stored plans, recovery roots, apply effects and the online budget model. Added, behind the same explicit contract selection and with no new write effect:

1. forge-free, bounded **integration proof kinds** beyond ancestry;
2. **merged-PR discovery** keyed by distinct head OID, with `--pr` as an override;
3. **bounded streaming** read paths so planning no longer fails at 64 KiB;
4. an explicit **configuration policy** (refuse versus neutralize) for read-only planning;
5. a **real-repository acceptance** task with before/after counts.

The numeric bounds below are proposed design decisions (marked *proposed*), derived from existing Spec 029 constants where one exists. Owner direction and conservative defaults, revisable: deletion rules are not stricter than the real risk. Different formatting or whitespace does not by itself prevent cleanup; strictness is kept only where content could really be lost (merge attributes, gitlink changes, rewritten history metadata, unsafe configuration, unbounded output, whitespace-significant file types). The forge-free proof phase has its own 60-second budget separate from the online 30-second phase; there is no second discovery endpoint; plan-only acceptance uses a source test runner and any CLI build stays owner-gated; reformatting that is not whitespace-only stays retained and the `git range-diff` evidence aid is a separate later Spec, not specified here.

### Design rationale: recoverable local deletion

`stw tidy apply` already records a recovery ref and a journal entry (branch name to tip OID) before it deletes a local branch, so a wrong local-branch deletion loses little. The recovery is exactly this: a local ref `refs/stw/recovery/v3/<plan>/<hash>` pointing at the deleted branch's tip commit, kept until removed by hand (Spec 029 data model; garbage collection cannot prune it), plus the journal entry. Only the tip commit and its history are preserved: earlier tips in the branch reflog and the `branch.<name>.*` configuration are not recorded (Spec 029 tidy-v3 contract), restoring is manual (`git branch NAME OID`), and the ref exists only in this clone (a re-clone loses it). Proof strictness is therefore reserved for cases where content could really be lost, not for cosmetic differences. Each relaxation below names the review counter-example it answers: H1 (a Python indentation change inside an `if`) is answered by the whitespace-significance guard of FR-003 and binary handling of FR-003a, not by blanket strictness; token joining (`rm -rf "$D" /` versus `rm -rf "$D"/`) is answered by a normalization that tolerates only indentation, trailing whitespace and CR; skipped merge commits by FR-003; H2 (add-then-revert) by a deletable class `no-net-change` that is never labelled integrated; `merge=union` (H-A), gitlinks, grafts, shallow clones, alternates and unsafe configuration remain refusals because they can make a proof false without any visible difference.

Nothing here authorizes a build, a release, a tag, an installation, an `apply` against a real repository or any activation. See [owner-gated work](#owner-gated-work).

## Dogfood evidence (measured on this repository, 2026-10-19)

Of 131 non-main local branches: 5 are **merge-noop** (merging them into the base changes nothing), 21 are **patch-id equivalent** (overlapping the 5), 33 would add content to the base, and 99 **conflict** with the base: their content was consolidated and reworked into other commits, so no forge-free proof exists. Offline v3 reported 93 of 149 refs `integration-not-proven` (rebase-merge rewrites SHAs so ancestry fails).

A per-commit cherry-pick simulation was evaluated and **rejected**: 1,087 of 1,750 commits conflict because stacked commits depend on their predecessors, so a conflict says nothing about integration. See [research](research.md#rejected-per-commit-cherry-pick-simulation).

## User scenarios and acceptance

### US1 — Recognize rebase- and squash-merged work without a forge (P1)

A maintainer plans a tidy offline. A branch whose commits keep their patch is `integration-proven` by `patch-exact` or `patch-id`; one whose cumulative content landed unchanged is proven by `merge-noop`; an ancestor still proves by `ancestor`; a branch with nothing unmerged is `no-net-change`. Each reports class, strength and bounded counts, and every non-ancestor class stays visible in the plan.

1. Fixture: rebase-merge of a three-commit branch yields `patch-exact` (3 of 3) and `merge-noop`.
2. Fixture: squash-merge yields `merge-noop` and no patch match.
3. Fixture: the base later reverts the integrated change: `patch-exact`/`patch-id` still match (history-equivalent, visible, recoverable) while `merge-noop` does not.
4. Fixture: add-then-revert branch (`B^{tree} == M^{tree}`): deletable with class `no-net-change`, not labelled integrated, recorded in the journal.
5. Fixture: indentation-only, trailing-whitespace-only and CRLF-only differences in a Go or Markdown file: deletable, class `integrated-modulo-whitespace`. The token-joining repro (`rm -rf "$D" /` on the branch, `rm -rf "$D"/` on the base) is unmatched and retained.
6. Fixture: the same indentation difference inside a Python `if` (or any whitespace-significant path, including a configured extra glob): retained `whitespace-significant-difference`. A binary file (by `binary`/`-diff`/`-text` attribute or NUL content) with any byte difference is retained; an identical binary patch is `patch-exact`. A branch containing a merge commit with a hand edit is retained `merge-commits-in-range` unless `merge-noop` proves it. A branch that adds X, reverts it and adds it again against a base with only add and revert is retained.
7. Fixture: reformatting that changes patch-ids beyond whitespace (import reordering, gofmt-style rewrap) with no `merge-noop`: retained `integration-not-proven` with counts; the evidence aid is a later Spec.
8. Fixture: `merge=union` repro: the branch deletes a line the base changed. Without the attribute `merge-tree` exits 1 (conflict); with `merge=union` (from `info/attributes` or an in-tree `.gitattributes`) it would exit 0 with the base tree, but the branch is `merge-attributes-present`, retained; a control tree without the attribute evaluates normally.
9. Fixture: one unmatched commit, a branch that would add content, or a conflict is retained with evidence counts only.

### US2 — Online evidence without per-branch hints (P1)

With `--online --remote NAME`, merged-PR evidence is discovered for every distinct unproven head OID without `--pr`. Several refs sharing one OID share one hint. `--pr OID=N` overrides discovery for that OID. Errors name the offending selector (`--pr` value, OID or ref).

### US3 — Plan large repositories (P1)

A repository with 149 branches/111 worktrees (and up to 1,024 of each) plans successfully in v1 and v3 within bounded memory. One record above a bound refuses with a named limit, never a truncated plan.

### US4 — Plan in repositories with submodules or hooks configuration (P1)

A repository or umbrella with `submodule.*`, `core.hooksPath` or `core.fsmonitor` configuration plans read-only; configured helpers provably never execute. Configuration that cannot be evaluated or that would execute under a planning command is refused or not-evaluated with the key class named. Apply keeps its existing refusals.

### Edge cases

- Merge commits in `M..B`; empty patches; a branch equal to the base; an unborn or symbolic ref; detached heads; a ref that is also a workspace-used ref (always retained, proof annotates only); more than 1,024 refs; SHA-256 repositories (patch-id and merge-tree are supported by native Git; PR discovery stays SHA-1/GitHub.com as in Spec 029).
- An object-database write by `merge-tree --write-tree` must never touch the inspected repository (see FR-009).
- Hostile branch names, config values and `.gitattributes` are data; they never become argv, endpoints or commands.

## Requirements

### Integration proofs (forge-free)

- **FR-001**: Closed set of deletion-eligible classes, strongest first: `ancestor`, `patch-exact`, `merge-noop`, `patch-id` (subclass `integrated-modulo-whitespace` when the verbatim patch differs), `no-net-change`, and `github-merged-head` (Spec 029). Each evaluated ref records class, a strength (`ancestry`, `exact-patch-history`, `content-present`, `history-equivalent`, `modulo-whitespace`, `nothing-unmerged`, `forge-attested`), base selector and OID, tip OID and bounded counts. The strongest proven class is the headline; every class other than `ancestor` stays visible in the plan and journal. `no-net-change` is never labelled integrated. Proof never overrides protection: selected bases, symbolic refs, workspace-used refs and uncertain targets retain regardless of proof (Spec 029 FR-010).
- **FR-002**: `ancestor`: the tip is reachable from the base OID (`git merge-base --is-ancestor TIP BASE`). Unchanged from Spec 029.
- **FR-003**: Patch equivalence. Let `U` be the base OID, `B` the tip and `M` the single merge base (`git merge-base --all` returning more than one is `not-evaluated: ambiguous-merge-base`). Branch side is every non-merge commit in `M..B`; base side is every non-merge commit in `M..U`. **Merge commits in `M..B`**: the patch classes require `skipped_merges = 0`, because a conflict resolution or hand edit inside a merge commit would be lost silently; with any merge commit in `M..B` only `ancestor`, `merge-noop` or `no-net-change` can prove the branch, otherwise it is retained with evidence `merge-commits-in-range`. Commits with an empty patch (tree equals its single parent's tree, from `git log --no-merges --format='%H %T %P' M..B`) are counted `empty`, excluded from `matched` and `unmatched` and never match. Per commit stw derives two digests from the bounded stream `git diff-tree --stdin -p --binary --full-index --no-ext-diff --no-textconv --no-renames --no-color -r --root`: the **verbatim** digest (`git patch-id --verbatim`: whitespace preserved, hunk line numbers and `index` lines ignored) and the **normalized** digest, a stw-computed SHA-256 over the same stream with these rules: drop `index` lines and the numbers of `@@` hunk headers (positions); keep file header, mode and rename lines and, per hunk, the sequence of `+`, `-` and context-space lines with the file path, so the context content stays part of the digest like in git's patch-id (the same line inserted after different context therefore differs); for each of those lines strip leading whitespace after the marker, trailing whitespace and a trailing CR; never alter whitespace between two non-whitespace characters. Context lines make a digest depend on the neighbouring code, so a rebase that changed neighbouring lines leaves the commit unmatched (as with git's own patch-id); `merge-noop` still covers it when the base has the final content. A line longer than 1 MiB is `proof-limit`. Git's own default patch-id (`git cherry`) is not used, because it removes whitespace everywhere (token joining such as `rm -rf "$D" /` versus `rm -rf "$D"/` would match). Matching is by multiset counts per digest: for each digest the base-side count must be at least the branch-side count (adding X, reverting it and adding it again does not match a base that only added and reverted it); the excess is `unmatched`. The class is `patch-exact` when every non-empty branch commit matches by verbatim digest; `patch-id` with subclass `integrated-modulo-whitespace` when every commit matches by normalized digest and at least one only by normalized digest; otherwise `partial`, retained. Guard: if any commit matched only by normalized digest touches a **whitespace-significant path** (default list in the [contract](contracts/integration-proofs.md#whitespace-significance-guard), extendable with the repeatable `--whitespace-significant GLOB`), the branch is retained with `whitespace-significant-difference` and up to 16 paths. Line endings (CR), trailing whitespace and indentation alone never retain a branch outside that list; import ordering and gofmt-style rewrap change the normalized digest and are unmatched.
- **FR-003a**: Binary paths. A path is binary when `git check-attr --source=<B^{tree}> -z --stdin binary diff text` reports the `binary` macro set, `diff` unset or `text` unset (so a text file with `-text` is treated as binary), and, when those attributes are unspecified, when Git's content detection says so (`git diff-tree --numstat` prints `-` for both counts, a NUL byte). Every command that decides or depends on it, `check-attr`, `diff-tree --numstat` and the `diff-tree -p` patch streams of both sides, runs with `git --attr-source=<B^{tree}>` (Git 2.40 or newer, within the 2.46.0/2.56.0 lanes), so no worktree file or untracked `.gitattributes` can change the classification or the patch text (an untracked `.gitattributes` with `e.raw diff` would otherwise turn a NUL file into a text patch and `-diff` the reverse). Git's `whitespace` attribute only configures whitespace warnings and is not used for significance. The pin does not cover `$GIT_DIR/info/attributes`: `$GIT_DIR/info/attributes` is still read by Git under `--attr-source` (measured on Git 2.47.3 and 2.56.0), so it is not pinned away. It is resolved exactly as the existing code resolves the git/common directory, read with a 1 MiB bound and no symlink following; when it contains any non-blank, non-comment line that defines or unsets `binary`, `diff`, `text`, `eol`, `merge` or `whitespace`, or a macro (`[attr]`), the attribute-dependent decisions (the binary classification of the patch classes and `merge-noop`) are `not-evaluated: info-attributes-present`; `ancestor` and `no-net-change` are unaffected, and the file is ignored when absent or only comments. Global, XDG and system attributes are excluded by the FR-019 environment. A commit touching any binary path matches only by verbatim digest (`patch-exact`, with `--binary`) and is never whitespace-tolerant.
- **FR-004**: `merge-noop` holds when all of: (1) `B^{tree}` differs from `M^{tree}` (equal trees are the separate class `no-net-change`, FR-004a, never labelled `merge-noop`); (2) `git merge-tree --write-tree --no-messages U B` exits 0 with a tree OID equal to `U^{tree}`; (3) no gitlink (mode 160000) path differs in `M..B` or `M..U` (`git diff-tree -r --raw --no-renames`), otherwise `not-evaluated: gitlink-change` because the merge engine would open submodule repositories; (4) exactly one merge base; (5) no `merge` attribute is defined by any attribute source (FR-010a). Exit 1 is `conflict`; a different tree is `would-add-content`. A tip that is an ancestor or equal to the base is reported `ancestor`; `merge-noop` is not evaluated.
- **FR-004a**: `no-net-change`: `B^{tree}` equals `M^{tree}` (for example WIP add then revert), with exactly one merge base. The branch has nothing unmerged to lose, so it is deletable with class `no-net-change`, shown in the plan and journal as such and never as integrated. It needs no merge-tree, attribute or gitlink check; grafts, shallow clones and alternates still make it `not-evaluated` because the merge base would be untrustworthy.
- **FR-005**: Nothing is proven by per-commit cherry-pick simulation, git's whitespace-erasing default patch-id, subject similarity, names, dates, authors, PR titles or user-named ranges. A branch whose patches differ beyond indentation, trailing whitespace and CR (token joining, import reordering, gofmt-style rewrap) and whose final content is not already in the base stays `integration-not-proven` with its evidence counts: no new proof is invented for reformatting now, and the `git range-diff` evidence aid is a later Spec. Because `merge-noop` compares final trees, it already proves such branches when the base contains the final content (T031 measures how many of the 131 branches). Not provable means retained, never deleted on a heuristic.
- **FR-006**: `--integration-proof KINDS` (comma-separated subset of `ancestor,patch-exact,merge-noop,patch-id,no-net-change`) narrows which classes may make a ref eligible. Default: all five. `--whitespace-significant GLOB` extends the guard list (FR-003). Duplicate or unknown kinds, or a malformed glob, are usage errors (exit 2 before native work). Classes not selected are neither run nor reported.
- **FR-007**: Per distinct tip OID the order is ancestor, no-net-change, patch-exact/patch-id (one pass computes both digests), merge-noop, then online PR evidence. All selected classes run so evidence is complete, within the budget.
- **FR-008**: Bounds (*proposed*). At most 1,024 evaluated tips (Spec 029 observation limit); per tip at most 1,024 branch-side and 4,096 base-side commits (pre-checked with `git rev-list --count --no-merges`; excess is `proof-limit` for the patch kinds only); at most 64 MiB of patch stream per tip for `patch-exact`. Every proof command has its own record bound, byte bound and line grammar in the [command bounds table](contracts/integration-proofs.md#command-bounds), including SHA-256 widths, each with its own test; a line outside its grammar or a bound exceeded makes that kind `not-evaluated` (`proof-limit` or the failure class), never a partial proof and never a failure of unrelated kinds. Time: per proof command 10 seconds (the Spec 029 per-observation context), per tip at most 20 seconds, and one forge-free proof phase of at most 60 seconds per planning operation with counters never reset. Exhaustion retains the remaining tips `integration-not-proven` with `proof-budget-exhausted`; the plan stays valid and says so. The total-time arithmetic is amended in Spec 029's contract amendments: offline plan = 10 s observation + 60 s proofs = 70 s; online plan = 10 + 60 + 30 s online evidence = 100 s; apply stays 60 s total including re-evaluation of the proofs it uses (FR-012), whose per-command 10 s and per-tip 20 s limits apply within that 60 s.
- **FR-009**: Proofs are read-only for the inspected repository. `merge-tree --write-tree` writes objects, so every proof command runs with `GIT_OBJECT_DIRECTORY` set to a fresh private mode-0700 directory removed on every exit path and `GIT_ALTERNATE_OBJECT_DIRECTORIES` naming only the repository's own object directory. Setting `GIT_OBJECT_DIRECTORY` makes Git ignore the repository's `objects/info/alternates`, so a repository that has an alternates file (also refused by Spec 029 `git-unsupported-metadata`) is `not-evaluated: unsupported-metadata` for all proofs, with a test. A test asserts the repository object directory, refs and `packed-refs` are byte-identical before and after planning. Failure to create the directory is `not-evaluated: object-dir-unavailable`.
- **FR-010**: Proof commands use fixed typed argv, `--` separators, full OIDs from an earlier native read, the FR-019 environment, `--no-ext-diff`, `--no-textconv`, no pager. `merge-noop` is `not-evaluated: git-unsafe-configuration` (class named) when the effective configuration defines `merge.*.driver` or an executable `filter.*.clean|smudge|process`; other proofs do not evaluate content through filters or drivers. A grafts file (`info/grafts`), a shallow file (`shallow`) or replace refs (`refs/replace/*`) make history untrustworthy: grafts or shallow make every proof `not-evaluated: history-override` (a graft can fake ancestry; a shallow history gives a wrong merge base), and replace refs are ignored by `--no-replace-objects` with the plan note `replace-refs-ignored`.
- **FR-010a**: Merge attributes. `merge=union`, `merge=binary`, `-merge` and macros such as `binary` change merge-ort's result without any `merge.*.driver`: a branch that deletes a line the base changed conflicts normally but with `merge=union` merges cleanly to the base tree and would be falsely proven. `merge-noop` is therefore `not-evaluated: merge-attributes-present` (retained, stable class) when any attribute source defines `merge` (set, unset, unspecified-reset or valued) for any path, or uses a macro that does. Sources checked, the same at plan and apply: every `.gitattributes` in `U^{tree}`, `B^{tree}` and `M^{tree}` (listed with `ls-tree -r -z`, read with `cat-file --batch`, at most 64 files of at most 1 MiB each, otherwise `proof-limit`), `$GIT_DIR/info/attributes`, the global, XDG and system attributes files (excluded by the private `HOME`/`XDG_CONFIG_HOME`, null `GIT_CONFIG_GLOBAL`/`GIT_CONFIG_SYSTEM`, `GIT_CONFIG_NOSYSTEM=1` and `GIT_ATTR_NOSYSTEM=1` of FR-019) and `core.attributesFile` (refused, FR-020). Parsing is conservative: any attribute list containing the token `merge` in any form (`merge`, `-merge`, `!merge`, `merge=...`), the macro `binary`, or a macro defined by an `[attr]` line that contains either, refuses. The merge command additionally pins `--attr-source=U^{tree}` so the worktree's checked-out files are never a source and plan and apply cannot diverge on worktree state. A clean tree without the attribute evaluates normally.
- **FR-011**: Forge-free proofs run without `--online` and without network, authentication or a state directory. Plan identity includes the proof policy version and the selected kinds (Spec 029 FR-027).
- **FR-012**: Apply re-evaluates the recorded class for each selected deletion immediately before the effect with fresh native state and the same constant planning configuration arguments (FR-019), including the whitespace-significance guard and binary rule, and retains on any change. The journal records branch name, tip OID, class, strength and subclass next to the Spec 029 recovery ref, with the limits stated in the design rationale; no new effect class. Recording `branch.<name>.*` configuration and the reflog tip is a follow-up decision (T035), not a requirement.

### Merged-PR discovery (fixes #81)

- **FR-013**: Online planning discovers merged-PR evidence by head OID with no `--pr` hint for every distinct unproven tip OID. Discovery is read-only GET against one explicitly resolved repository and uses only the closed endpoint set in [PR discovery](contracts/pr-discovery.md#endpoint-set): the repository record, the closed-PR collection (up to 10 pages of 100) and the per-PR read already allowed by Spec 029. No write, redirect to another host or compression (Spec 029 online contract). No second endpoint is added by this Spec.
- **FR-014**: Hints and evidence are keyed by distinct OID. Several refs with the same OID share one hint and one evidence record listing every ref. A repeated identical `--pr OID=N` is idempotent; the same OID with a different number is a usage error naming the OID and both selectors.
- **FR-015**: `--pr OID=N` overrides discovery for that OID only and still passes full tuple validation (Spec 029 FR-007). A hint for an OID no selected ref carries is a usage error naming the OID.
- **FR-016**: Every usage or discovery refusal names the offending selector: full flag text (`--pr <value>`), the OID and affected refs, escaped and truncated to the Spec 029 4,096-byte bound.
- **FR-017**: Discovery coverage is explicit and amends Spec 029's refusal of a full final page without proven exhaustion (amendment 5). Positive evidence stays usable: an exact-head merged PR that is found and passes the full Spec 029 tuple verification and re-read is proof for that OID regardless of collection completeness. Only absence is inconclusive: when the closed collection ends within the page and record bounds, coverage is `complete` and OIDs without a match are `integration-not-proven` with `no-merged-pr`; when a bound is reached, coverage is `incomplete` and OIDs without a found PR are retained `integration-not-proven` with `discovery-incomplete`; the plan does not refuse. Several admissible PRs for one OID need an explicit hint (Spec 029 FR-008).
- **FR-018**: Discovery shares the Spec 029 FR-025 online budget unchanged: one 30-second online plan deadline, at most 128 HTTP requests and 32 MiB raw response bytes per run, shared with tracking-ref reads and counting failures. Request accounting, taken from the baseline source and cited: the plan path costs one repository read when the session opens (`internal/hosting/tidy_evidence_session.go:224`), one repository revalidation at the start of `DiscoverPullRequests` (`internal/hosting/tidy_evidence_pr.go:283`), at most 10 closed-PR pages (`discoverPRHints`, `tidy_evidence_pr.go:209`, `maxPages = 10` at `internal/hosting/transport.go:23`) and one PR read per candidate (`readPullRequest`, `tidy_evidence_pr.go:303`); the total request ceiling is 128 (`tidyMaxRequests`, `tidy_evidence_session.go:20`). Formula: candidate reads fit = (128 - fixed repository reads - page reads) / cost per candidate = (128 - 2 - 10) / 1 = 116 with all ten pages read; with fewer pages more fit. The cost is per candidate PR, not per OID: an OID with two candidate PRs costs two reads. The two-request pair (repository revalidation plus PR read) is `RevalidatePullRequest` (`tidy_evidence_pr.go:159-173`), which runs at apply, inside the apply run's own budget and outside this plan budget; a literal reading of the Spec 029 online contract (online.md "re-read repository ID with it") would make it three per PR, but the source is the baseline and T022 asserts the exact counts against it. Re-reads proceed in ascending OID order; when the remaining budget cannot cover the next candidate PR read, that OID and all later ones are `integration-not-proven` with `discovery-budget-exhausted` and the plan completes with a note. The 60-second forge-free proof phase (FR-008) runs first as its own phase; the online phase keeps its own 30 seconds, so the sequential totals are those of FR-008. T021 measures why #81 needed hints; a second endpoint is out of scope and revisited only on that evidence in a later amendment.

### Configuration policy (fixes #79)

- **FR-019**: Planning commands (observation, reads and proofs) run with the sanitized environment and one constant argument list shared by planning and apply re-evaluation: no inherited `GIT_*` override, including `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_*`/`GIT_CONFIG_VALUE_*`; every native command of the proofs additionally runs with a private empty `HOME` and `XDG_CONFIG_HOME` (temporary directories owned by the process, removed afterwards), `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` set to the platform null file (`/dev/null`), `GIT_CONFIG_NOSYSTEM=1` and `GIT_ATTR_NOSYSTEM=1` (so no global, XDG or system configuration or attributes file applies); `-c core.hooksPath=/dev/null -c core.fsmonitor=false -c submodule.recurse=false -c core.untrackedCache=false -c merge.renormalize=false -c merge.renames=true -c merge.directoryRenames=conflict -c merge.renameLimit=1000 -c diff.renames=true -c diff.renameLimit=1000 -c core.autocrlf=false -c gc.auto=0 -c maintenance.auto=false -c protocol.ext.allow=never`, `--no-optional-locks`, `--no-replace-objects`, `GIT_NO_LAZY_FETCH=1`. A separate admission read lists effective configuration with origins (global and system included) for classification and plan notes; it executes no helper.
- **FR-020**: Classification ([policy](contracts/configuration-policy.md)). **Neutralized for planning** (recorded plan note, plan succeeds): `core.hooksPath`, `core.fsmonitor`, `submodule.*`, `core.pager`, `core.editor`, `core.sshCommand`, `core.askPass`, `credential.*`, `gpg.*`, `diff.external`, `diff.<driver>.textconv`. **Not-evaluated for a proof only** (plan still succeeds): `merge.*.driver`, executable `filter.*` and any merge attribute (class `merge-attributes-present`) for `merge-noop`; grafts, shallow, alternates for every proof (FR-009, FR-010). **Refused, no plan** (class `git-unsafe-configuration` or the existing Spec 029 class, unchanged): `hook.*`, `include.*` only as `includeIf.*`, `core.attributesFile`, `extensions.worktreeConfig`, `extensions.partialclone`, `remote.*.promisor`, `core.alternateRefsCommand`, `core.sparseCheckout*`, and the reserved sentinel `filter.unspecified|unset|set.*` names. Plain `include.path` is evaluated by Git and classified by effective keys. Whatever stage2 does today for other executable `filter.*` in the safety collector stays (T002 confirms). Unknown executable-looking keys are refused by class.
- **FR-021**: Justification and unchanged items. Only `core.hooksPath`, `core.fsmonitor` and `submodule.*` change from refused to neutralized: no read-only planning command runs hooks, fsmonitor or `git submodule`, and the arguments of FR-019 disable them on every command; this is the precedent already used for inventory and release reads. `hook.*` stays refused because command-line `core.hooksPath` does not neutralize config-based hooks; `core.attributesFile` stays refused because it changes content evaluation. The default `.git/hooks` fingerprint remains bound into the safety digest unchanged: a changed or executable hook changes the plan and apply refuses a hook-running effect. Gitlinks are data: no `git submodule`, no descent by this Spec's commands; `merge-noop` is not evaluated when a gitlink differs (FR-004). A worktree retirement target with an initialized submodule retains `submodule-present`.
- **FR-022**: Apply keeps every existing refusal. Neutralization is planning-only: the plan records the neutralized configuration digest and a per-plan `apply_effect`; apply refuses effects whose hooks or helpers would execute (for example a `reference-transaction` hook for a ref deletion), naming the class, never skipping hooks silently.
- **FR-023**: Sentinel test for every class: a configured helper writes a marker file; the marker is absent after planning; plan notes or refusals name the class. Mutants (remove a `-c` item, inherit `GIT_CONFIG_PARAMETERS`/`GIT_CONFIG_COUNT`, inherit global config) must fail the matrix.

### Bounded planning (fixes #80)

- **FR-024**: The v1 and v3 reference and registration reads stream through the existing bounded native stream executor, parsing record by record; whole-output buffering at 64 KiB (`nativeOutputLimit`) no longer applies to `for-each-ref` and `worktree list --porcelain -z`. Memory is bounded by one record plus the parsed set.
- **FR-025**: Hard bounds remain refusals (*proposed*, Spec 029 constants): at most 1,024 references and 1,024 registrations (`observationLimit`); each record at most 4,224 bytes; each stream at most 4,325,376 stdout and 65,536 stderr bytes. One record or byte over refuses with `git-observation-limit` or `git-output-limit` naming the stream, never a truncated plan.
- **FR-026**: v3-only documentation is not chosen; v1 is repaired so v1/v2 callers keep working with unchanged published bytes and result shape. 64 KiB stays for non-collection reads.

### Acceptance and effects

- **FR-027**: Acceptance: a plan-only source test runner (in-process, no build) plans this repository and the Anchorage umbrella read-only with a temporary state directory and private object directory, never `apply`, and records counts before (stage2 baseline) and after per proof kind and disposition. A CLI-binary lane needs a separately named owner build authorization; without it that lane is a recorded gap.
- **FR-028**: Every behavior is first covered by failing tests using temporary repositories and deterministic transport doubles (constitution IV); no test touches a real user repository except the read-only acceptance runner of FR-027.
- **FR-029**: Schema: additions are additive to the unpublished v3 result and plan ([data model](data-model.md)); v1/v2 schemas and fixtures stay byte-identical; v3 is published only with accepted implementation.
- **FR-030**: No new network write, remote ref effect or native write effect; proof commands write only to their private temporary object directory.

## Success criteria

- **SC-001**: US1 fixtures (rebase-merge, squash-merge, revert-after-merge, no-net-change, whitespace-only in code and in whitespace-significant files, reformatting retained, merge-attribute repro, empty commit, partial, conflict) produce exactly the stated proof kinds, strengths and counts offline, with zero network and zero repository object/ref changes.
- **SC-002**: On a generated 150-branch/120-worktree fixture, v1 and v3 plans succeed; fixtures at 1,024 refs/registrations pass and at 1,025 refuse with the named limit; peak buffered stdout in the parser is one record.
- **SC-003**: Every row of the configuration matrix (C1..C37) produces its stated result with helper markers absent, and mutants M1..M7 are killed.
- **SC-004**: Online fixtures with 40 refs sharing 12 OIDs plan with no `--pr`, stay within 128 requests; a separate fixture with 120 distinct merged-PR OIDs, one candidate each, spread over ten full collection pages performs 2 repository reads, 10 page reads and exactly 116 candidate PR reads (128 requests in total) and reports the last 4 OIDs in ascending order `discovery-budget-exhausted`; duplicate/mismatched hints fail with selector-naming messages; an incomplete collection is reported `incomplete`, found PRs remain proof and missing ones are `discovery-incomplete`, never absence.
- **SC-005**: Published v1/v2 schemas, fixtures and old stored-plan bytes are unchanged; v3 results validate against the candidate schema and agree with human output.
- **SC-006**: Recorded before/after counts for this repository (baseline 93 of 149 `integration-not-proven` offline) and the Anchorage umbrella exist in a verification note, with every unexplained retention listed. No cleanup was applied.

## Owner-gated work

Not permitted without explicit owner authorization naming the one operation (workspace `AGENTS.md`): building or installing a CLI artifact, running a built `stw`, `apply` against any real repository, tag, release, publication, repository/ruleset settings, merge, consumer image activation. Source tests, formatting, vet and test-compiler verification may run automatically. The defaults listed under scope are decisions revisable by the owner: relaxed patch-id and no-net-change deletion with the whitespace-significance guard, the bounds, the separate forge-free phase and the deferral of the range-diff aid.

## Key entities

- Proof evidence: kind, strength, base selector/OID, tip OID, counts, policy version, classification (`proven`, `partial`, `would-add-content`, `conflict`, `no-net-change`, `whitespace-significant-difference`, `merge-commits-in-range`, `not-evaluated`; reasons include `info-attributes-present`).
- Discovery record: OID, hint number and identities, covered refs, coverage (`complete`, `incomplete`), source (`discovered`, `hint`).
- Configuration note: key class, neutralized or refused, digest, effect on apply.

## Assumptions and scope

Same-user cooperative repositories (Spec 029). Native Git minimum/current lanes as Spec 029 (2.46.0 / 2.56.0); `merge-tree --write-tree` requires Git 2.38+. jj and GitButler backends are out of scope: no Git writes for them, no proof kinds are claimed for them. `merge-noop` proves present content; patch equivalence proves that an equal change existed on the base at some point, not that it is still present; the plan labels it and recovery bounds the risk. Consolidated work remains retained; a range-diff evidence aid for it is a separate later Spec, not specified here.
