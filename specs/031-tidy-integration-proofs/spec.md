# Feature Specification: Tidy git-native integration proofs, PR discovery and bounded planning

**Branch**: `codex/spec-tidy-integration-proofs` | **Created**: 2026-10-19
**Status**: Draft specification; no runtime implementation. Requires independent review before tasks start. Restructured on owner direction (simple git-native proofs plus a review report and reviewer decisions).
**Input**: Dogfooding `stw tidy` (Spec 029 contract 3) on this repository (149 local branches, 111 worktrees, GitHub rebase-merge) and on the Anchorage umbrella (submodules). Forge issues: #79 (plan refused for `submodule.*` or `core.hooksPath` configuration), #80 (v1 plan fails at the 64 KiB `nativeOutputLimit` around 146 branches/86 worktrees), #81 (v3 online plan needs explicit `--pr OID=N`; duplicate OIDs rejected as duplicate hints; offline rebase-merge integration is not detected: 93 of 149 refs `integration-not-proven`).

## Scope and decision status

This Spec **amends** Spec 029 (local tidy with explicit integration evidence) where stated in [its contract amendments](../029-tidy-dogfood-safety/contract-amendments.md#spec-031-amendments): Spec 029 treats patch similarity as optional supporting information only; this Spec makes git's own patch equivalence a default deletion proof (with a visible whitespace flag), adds `merge-noop` and `no-net-change`, and turns every case that is not provable but not hopeless into a **review report** that a human or an AI can judge, plus a **decision file** that records the reviewer's verdict. Spec 029 otherwise remains the owner of contract 3 commands, stored plans, recovery roots, apply effects and the online budget model. Added, behind the same explicit contract selection and with no new write effect on the repository:

1. simple, forge-free, bounded **integration proofs** (`ancestor`, git `patch-id`, `merge-noop`, `no-net-change`);
2. a **review report** (Markdown for humans, JSON for AI) for every candidate that needs review, including `git range-diff` pairing against a user-named consolidation range;
3. **reviewer decisions** (`--decisions FILE`) as evidence input, never authorization;
4. **merged-PR discovery** keyed by distinct head OID, with `--pr` as an override;
5. **bounded streaming** read paths so planning no longer fails at 64 KiB;
6. an explicit **configuration policy** (refuse versus neutralize) for read-only planning;
7. a **real-repository acceptance** with counts per bucket, report samples and an AI review step.

Owner direction: do not over-engineer whitespace or attribute detection; it is usually an edge case. Cheap, clear guards that prevent real loss are kept, and each guard produces a report entry with a stable reason, not a bespoke refusal class. The numeric bounds below are proposed design decisions (marked *proposed*), derived from existing Spec 029 constants where one exists. The forge-free proof phase has its own 60-second budget separate from the online 30-second phase; there is no second discovery endpoint; plan-only acceptance uses a source test runner and any CLI build stays owner-gated.

### Design rationale: recoverable local deletion and evidence-only review

`stw tidy apply` already records a recovery ref and a journal entry (branch name to tip OID) before it deletes a local branch, so a wrong local-branch deletion loses little. The recovery is exactly this: a local ref `refs/stw/recovery/v3/<plan>/<hash>` pointing at the deleted branch's tip commit, kept until removed by hand (Spec 029 data model; garbage collection cannot prune it), plus the journal entry. Only the tip commit and its history are preserved: earlier tips in the branch reflog and the `branch.<name>.*` configuration are not recorded (Spec 029 tidy-v3 contract), restoring is manual (`git branch NAME OID`), and the ref exists only in this clone (a re-clone loses it). Strictness is therefore reserved for cases where content could really be lost, and everything else is made easy to judge. A reviewer decision is evidence for the plan, never authorization: apply still needs the existing explicit owner authorization and the recovery journal.

Nothing here authorizes a build, a release, a tag, an installation, an `apply` against a real repository or any activation. See [owner-gated work](#owner-gated-work).

## Dogfood evidence (measured on this repository, 2026-10-19)

Of 131 non-main local branches: 5 are **merge-noop** (merging them into the base changes nothing), 21 are **patch-id equivalent** (overlapping the 5), 33 would add content to the base, and 99 **conflict** with the base: their content was consolidated and reworked into other commits, so no forge-free proof exists. Offline v3 reported 93 of 149 refs `integration-not-proven` (rebase-merge rewrites SHAs so ancestry fails).

The 99 conflicting branches are the main target of the review report: their content was consolidated and reworked, so no forge-free proof exists and a reviewer must see what the base does not yet contain.

A per-commit cherry-pick simulation was evaluated and **rejected**: 1,087 of 1,750 commits conflict because stacked commits depend on their predecessors, so a conflict says nothing about integration. See [research](research.md#rejected-per-commit-cherry-pick-simulation).

## User scenarios and acceptance

### US1 — Recognize rebase- and squash-merged work without a forge (P1)

A maintainer plans a tidy offline. A branch whose commits keep their patch is proven by git's own `patch-id`; one whose cumulative content landed unchanged by `merge-noop`; an ancestor by `ancestor`; a branch with nothing unmerged is `no-net-change`.

1. Fixture: rebase-merge of a three-commit branch is `patch-id` proven (3 of 3) and `merge-noop`.
2. Fixture: squash-merge is `merge-noop` and has no patch match.
3. Fixture: the base later reverts the integrated change: `patch-id` still matches (labelled, recoverable) while `merge-noop` does not.
4. Fixture: add-then-revert branch (`B^{tree} == M^{tree}`) is deletable as `no-net-change`, never labelled integrated.
5. Fixture: a whitespace-only difference (indentation, trailing whitespace, CRLF, or joined tokens such as `rm -rf "$D" /` versus `rm -rf "$D"/`) is `patch-id` equivalent but flagged `whitespace-differs`: needs review, listed in the report with the whitespace made visible, deletable only with `--accept-whitespace-differences` or a cleared decision.
6. Fixture: a branch containing a merge commit, a partial match, a multiset mismatch (add X, revert, add X against a base with only add and revert), a gitlink change, a `merge=union` attribute, any `info/attributes` content, or a `diff` attribute needs review with the matching reason; none is deleted by default.
7. Fixture: two different binary changes to one path never match (git hashes the binary patch, not the path).

### US2 — Judge what is not provable (P1)

For each candidate that needs review, `stw tidy plan --report-dir DIR` writes a Markdown report a human can read and a JSON report an AI can evaluate without running git: the commits, why each proof failed, one readable diff of what the base does not yet contain, candidate matching base commits, an optional pairing against a consolidation range, and a suggested verdict.

### US3 — Record the verdict (P1)

A reviewer writes a decision file (`integrated`, `keep`, `drop`, with reason, reviewer and kind), bound to the exact tip OID. `stw tidy plan --decisions FILE` consumes it: `integrated` and `drop` become deletable (`reviewed-integrated`, `reviewed-drop`), `keep` stays; the decision is recorded in the plan and the recovery journal. Apply still requires owner authorization.

### US4 — Online evidence without per-branch hints (P1)

With `--online --remote NAME`, merged-PR evidence is discovered for every distinct unproven head OID without `--pr`. Several refs sharing one OID share one hint. `--pr OID=N` overrides discovery for that OID. Errors name the offending selector.

### US5 — Plan large repositories (P1)

A repository with 149 branches/111 worktrees (and up to 1,024 of each) plans successfully in v1 and v3 within bounded memory. One record above a bound refuses with a named limit, never a truncated plan.

### US6 — Plan in repositories with submodules or hooks configuration (P1)

A repository or umbrella with `submodule.*`, `core.hooksPath` or `core.fsmonitor` configuration plans read-only; configured helpers provably never execute. Configuration that cannot be evaluated or would execute under a planning command is refused with the key class named. Apply keeps its existing refusals.

### Edge cases

- Merge commits in `M..B`; empty patches; a branch equal to the base; an unborn or symbolic ref; detached heads; a ref that is also a workspace-used ref (always retained, proof annotates only); more than 1,024 refs; SHA-256 repositories (patch-id and merge-tree are supported by native Git; PR discovery stays SHA-1/GitHub.com as in Spec 029).
- An object-database write by `merge-tree --write-tree` must never touch the inspected repository (see FR-009).
- Hostile branch names, commit subjects, config values and `.gitattributes` are data; they never become argv, endpoints or commands.

## Requirements

### Integration proofs (forge-free)

- **FR-001**: Dispositions and classes. Each evaluated ref is `proven`, `needs-review` or `retained`. Deletable-by-proof classes, strongest first: `ancestor`, `patch-id`, `merge-noop`, `no-net-change`, `github-merged-head` (Spec 029); decision classes `reviewed-integrated` and `reviewed-drop` (FR-039). Each records class, base selector and OID, tip OID and bounded counts. Strength labels are `ancestry`, `history-equivalent`, `content-present`, `nothing-unmerged`, `forge-attested`, `reviewer-decision`. `no-net-change` is never labelled integrated. Proof never overrides protection: selected bases, symbolic refs, workspace-used refs and uncertain targets are `retained` regardless of proof (Spec 029 FR-010).
- **FR-002**: `ancestor`: the tip is reachable from the base OID (`git merge-base --is-ancestor TIP BASE`). Unchanged from Spec 029.
- **FR-003**: `patch-id` uses git's own semantics and nothing custom. Let `U` be the base OID, `B` the tip and `M` the single merge base. Branch side is every non-merge commit in `M..B`, base side every non-merge commit in `M..U`; both are hashed with `git log --no-merges -p --binary --no-ext-diff --no-textconv` piped to `git patch-id --stable` (the default patch-id, the semantics of `git cherry`; binary changes are hashed by content, so two different binary changes never match on path alone, measured on Git 2.47.3 and 2.56.0). The class holds when at least one non-empty branch commit exists, every non-empty branch commit has an equal patch-id on the base side, the multiset counts hold (for each patch-id the base-side count is at least the branch-side count) and no review reason of the [reason table](contracts/integration-proofs.md#review-reasons) applies. Empty commits (tree equals its single parent's tree) are counted `empty` and never match. Review reasons raised here: `partial-match`, `multiset-mismatch`, `merge-commits-in-range` (any merge commit in `M..B`: a conflict resolution or hand edit inside a merge would be lost silently, so only `ancestor`, `merge-noop` or `no-net-change` can prove such a branch), `ambiguous-merge-base`.
- **FR-003w**: Whitespace flag. For each branch commit matched by the default patch-id, stw also computes `git patch-id --verbatim` (whitespace preserved) over the same patch stream. When no matched base commit has an equal verbatim patch-id and the commit touches no binary path (FR-003b), the branch is still `patch-id` equivalent but flagged `whitespace-differs`: it needs review, appears in the report with the whitespace-only differences made visible (FR-033), and is deletable only with the policy flag `--accept-whitespace-differences` (the class stays `patch-id`, the flag stays visible in the plan) or with a cleared decision (FR-040). No other whitespace or formatting rule exists: there is no custom digest, no significant-file list and no normalization. Reformatting that changes the default patch-id is simply not matched and, if `merge-noop` does not prove it, gets a report entry (including the unintegrated diff).
- **FR-003b**: Binary paths, light. Whether a path is binary is decided by Git itself: `git --attr-source=<tip tree> diff-tree --numstat` in the private clean environment prints `-` for a binary path (attributes are honoured by Git; stw interprets no attributes and scans nothing for this decision). It is used only (a) for report rendering: a binary path is shown as "binary file changed" with the old and new blob OIDs and sizes, never as a content diff (FR-033), and (b) to never raise `whitespace-differs` for a binary path, because `patch-id` hashes a binary change by its blob ids and is therefore exact: two different binary changes to one path never match (measured on Git 2.47.3 and 2.56.0: different blobs gave different patch-ids, the same blob change gave `-` in `git cherry`). There are no further binary classes, refusals or matrix rows.
- **FR-004**: `merge-noop` holds when `B^{tree}` differs from `M^{tree}`, there is exactly one merge base, no gitlink (mode 160000) path differs in `M..B` or `M..U`, no attribute reason applies, and `git merge-tree --write-tree --no-messages U B` exits 0 printing a tree equal to `U^{tree}`. Exit 1 gives review reason `conflict`; a different clean tree gives `would-add-content`; a gitlink difference gives `gitlink-change` (the merge engine would open submodule repositories). A tip that is an ancestor or equal to the base is reported `ancestor`.
- **FR-004a**: `no-net-change`: `B^{tree}` equals `M^{tree}` (for example WIP add then revert), with exactly one merge base. The branch has nothing unmerged to lose, so it is deletable as `no-net-change`, shown in the plan and journal as such. It needs no merge-tree or attribute check; grafts, shallow clones and alternates still stop it (FR-010).
- **FR-005**: Nothing else proves integration: not per-commit cherry-pick simulation, subject similarity, names, dates, authors, PR titles, a user-named range or a reviewer's opinion alone (a decision is FR-039..FR-041 evidence, and range pairing is report evidence only, FR-037).
- **FR-006**: `--integration-proof KINDS` (comma-separated subset of `ancestor,patch-id,merge-noop,no-net-change`, default all) narrows the proof classes; `--accept-whitespace-differences` (FR-003w) is a separate boolean policy flag. Duplicate or unknown kinds are usage errors (exit 2 before native work). Classes not selected are neither run nor reported.
- **FR-007**: Per distinct tip OID the order is ancestor, no-net-change, patch-id (default and verbatim in one pass), merge-noop, then online PR evidence. All selected classes run so evidence is complete, within the budget.
- **FR-008**: Bounds (*proposed*). At most 1,024 evaluated tips (Spec 029 observation limit); per tip at most 1,024 branch-side and 4,096 base-side commits (pre-checked with `git rev-list --count --no-merges`; excess is review reason `proof-limit` for `patch-id` only); at most 64 MiB of patch stream per tip. Every proof command has its own record bound, byte bound and line grammar in the [command bounds table](contracts/integration-proofs.md#command-bounds), including SHA-256 widths, each with its own test; a violation makes that class `needs-review` with `proof-limit`, never a partial proof. Time: per proof command 10 seconds (Spec 029 per-observation context), per tip at most 20 seconds, one forge-free proof phase of at most 60 seconds per planning operation with counters never reset; exhaustion gives the remaining tips `proof-budget-exhausted` and the plan stays valid and says so. The total-time arithmetic is amended in Spec 029's contract amendments: offline plan = 10 + 60 = 70 s; online plan = 10 + 60 + 30 = 100 s; apply stays 60 s total. The review report has its own bounds (FR-035).
- **FR-009**: Proofs and the report are read-only for the inspected repository. `merge-tree --write-tree` writes objects, so every proof and report command runs with `GIT_OBJECT_DIRECTORY` set to a fresh private mode-0700 directory removed on every exit path and `GIT_ALTERNATE_OBJECT_DIRECTORIES` naming only the repository's own object directory. Setting it makes Git ignore the repository's `objects/info/alternates`, so a repository with an alternates file (also refused by Spec 029 `git-unsupported-metadata`) is a hard stop `unsupported-metadata`. A test asserts the repository object directory, refs and `packed-refs` are byte-identical before and after planning. Failure to create the directory is review reason `object-dir-unavailable`.
- **FR-010**: Proof commands use fixed typed argv, `--` separators, full OIDs from an earlier native read, the FR-019 environment, `--no-ext-diff`, `--no-textconv`, no pager. Hard stops, which no decision can clear because the history itself is untrustworthy: a grafts file (`info/grafts`) or shallow file makes every proof `history-override`; an alternates file is `unsupported-metadata`. Replace refs are ignored by `--no-replace-objects` with the plan note `replace-refs-ignored`.
- **FR-010a**: Attribute guards, all producing review reasons instead of refusals. Every attribute-dependent command (`merge-tree`, the `diff-tree`/`log -p` streams, `check-attr`) runs with `git --attr-source=<tree>` pinned to the tip tree (`U^{tree}` for `merge-tree`) so worktree and untracked `.gitattributes` never apply, and with the FR-019 private environment so global, XDG and system attributes never apply. Reasons: `attribute-source` for `patch-id` and `merge-noop` when `$GIT_DIR/info/attributes` (the common git directory, also through linked worktrees) exists and is a symlink, a special file, larger than 1 MiB or has any non-blank, non-comment line (Git still applies it under `--attr-source`, so it cannot be pinned away); `merge-attribute` for `merge-noop` when any `.gitattributes` in the `U`, `B` or `M` trees defines or uses `merge` or the `binary` macro (the scan is conservative: any attribute list containing the token `merge` in any form or `binary`, or a macro defined by an `[attr]` line that contains either; at most 64 files of at most 1 MiB each, otherwise `proof-limit`), because `merge=union` makes a branch that deletes a line the base changed merge cleanly to the base tree; `diff-attribute` for `patch-id` when `check-attr diff` on any path touched by a branch commit reports anything but `unspecified`; `merge-driver` for `merge-noop` when `merge.*.driver` or an executable `filter.*.clean|smudge|process` is configured.
- **FR-011**: Forge-free proofs run without `--online` and without network, authentication or a state directory. Plan identity includes the proof policy version, the selected kinds, `--accept-whitespace-differences` and the decision file digest (Spec 029 FR-027).
- **FR-012**: Apply re-evaluates the recorded class for each selected deletion immediately before the effect with fresh native state and the same constant planning configuration arguments (FR-019), and retains on any change; for `reviewed-*` classes it re-checks the exact tip OID and protections. The journal records branch name, tip OID, class, flags and, for decisions, who, what and why, next to the Spec 029 recovery ref, with the limits stated in the design rationale; no new effect class. Recording `branch.<name>.*` configuration and the reflog tip is a follow-up decision (T045), not a requirement.

### Review report and decisions

- **FR-031**: Needs review. Every ref that is not `proven`, not protected and not a hard stop is `needs-review` with one or more reasons from the closed [review reason table](contracts/integration-proofs.md#review-reasons) (the single definition of each reason). `retained` refs (protected or hard stop) are never offered a decision but are listed in the report summary with their reason and `clearable: false`.
- **FR-032**: Emission. `stw tidy plan` (contract 3, offline or online) always includes in its v3 result a `review_summary` (counts per bucket and reason). With `--report-dir ABS` it also writes `tidy-report.md` and `tidy-report.json`, two renderings of the same data ([review report contract](contracts/review-report.md)), for every `needs-review` ref up to the bounds of FR-035. Files are written only to the owner-named absolute directory, never into any repository, worktree, git directory or the state directory (refused otherwise), created mode 0600 exclusively without following symlinks, written as temporary files and renamed; an existing target is a usage error. A write failure fails the plan (exit 1) with nothing partially written.
- **FR-033**: Markdown report for humans. Per branch: a short header (name, tip OID, base, merge base, reasons, suggested verdict), the commits (OID, subject, author, date), which proofs were tried and why each failed, one readable unified diff of what the base does **not yet contain** (the result tree `R` of `git merge-tree --write-tree U B`, shown as `git diff U^{tree} R`, i.e. only the unintegrated change; for a conflicting merge the diff is of the result tree with conflict markers and the conflicted paths are listed), candidate matching base commits (same patch-id, or same subject) and the optional range pairing (FR-037). A binary path is shown as "binary file changed" with old and new blob OIDs and sizes and no content (FR-003b). When the only difference is whitespace (the diff is empty under `-w` but not without), the diff is rendered with whitespace made visible (tab as `→`, trailing space as `·`, CR as `␍`) and the section says so. Large diffs are truncated with exact counts.
- **FR-034**: JSON report for AI, stable schema `schema_version: 1` (fields in the contract): `summary`, `base`, `entries[]` with `branch`, `tip_oid`, `reasons`, `commits`, `proofs_tried`, `unintegrated_diff` (stat and hunks with file and line ranges, `whitespace_only`, truncation markers), `candidate_base_commits`, `range_pairing`, `suggested_verdict` (`verdict`, `confidence`, `basis`), `questions` (fixed templates) and `allowed_decisions`. An AI reviewer can classify each branch from this file alone, without running git. Deterministic ordering (ref name), no timestamps in the data, byte-identical across runs for identical input.
- **FR-035**: Bounds (*proposed*) with explicit truncation markers carrying exact counts (`shown`, `total`, unit): at most 256 entries; per entry at most 50 commits, 5 candidate base commits, one diff of at most 64 KiB, 1,000 lines and 16 files (hunks beyond are counted), 256 range-pairing rows; Markdown at most 4 MiB and JSON at most 4 MiB in total; an entry beyond the entry bound is listed by name and reasons only with the omitted count. Every report git command is bounded in the command bounds table.
- **FR-036**: Safety of content. The report contains only metadata, the unintegrated diff and the matching commits' subjects; never other file contents. Credentials in URLs (`scheme://user:secret@host`) are replaced by `scheme://<redacted>@host` in every emitted string. The unintegrated diff can still contain secrets that are in the branch; files are 0600, documented as sensitive, and the limitation is stated in the contract. Subjects, names and paths are data: escaped for Markdown, never interpreted.
- **FR-037**: Consolidation range evidence aid (previously deferred, now in scope). `--consolidation-range RANGE` (repeatable up to 4, each `A..B` of full or resolvable refs, at most 256 commits, resolved to OIDs before use and refused when malformed or oversized) pairs each reported branch's commits with the range using `git range-diff` and reports the pairs (`=`, `!`, `<`, `>`) as evidence `superseded-candidate` in both renderings. It is evidence only and never a deletion proof; it changes at most the suggested verdict.
- **FR-038**: Suggested verdict, deterministic. `verdict` is one of `obviously-integrated`, `looks-superseded`, `has-real-unmerged-content`, `unclear`, with `confidence` high, medium or low from the [verdict table](contracts/review-report.md#suggested-verdict): `obviously-integrated` when the unintegrated diff is empty or whitespace-only; `looks-superseded` when a named range pairs every non-empty branch commit; `has-real-unmerged-content` when the unintegrated diff is non-whitespace and unpaired; otherwise `unclear` (conflicts, merge commits, attribute reasons, truncation). It is a suggestion for the reviewer, never a decision.
- **FR-039**: Decision file ([decisions contract](contracts/decisions.md)): JSON `{schema_version: 1, decisions: [...]}` with per decision `branch` (full ref), `tip_oid`, `decision` (`integrated`, `keep`, `drop`), `reason` (at most 1,024 bytes), `reviewer` (at most 128 bytes), `kind` (`human`, `ai`). At most 1,024 decisions, file at most 1 MiB, absolute regular file not a symlink. Refusals (usage error, exit 2, before native work): too large, unknown schema version or field, malformed JSON, duplicate branch, missing field, invalid enum, a `drop` or `integrated` without a reason. A decision whose `tip_oid` is not the ref's current tip is ignored with the plan note `stale-decision` (never an error).
- **FR-040**: Consumption. `stw tidy plan --decisions FILE` makes `integrated` deletable as `reviewed-integrated` and `drop` as `reviewed-drop`; `keep` is `retained` with `reviewed-keep`. A decision clears only `needs-review` refs (not protected refs, not hard stops, not refs with no decision). The decision (who, kind, what, why, tip OID) is recorded in the plan and the recovery journal.
- **FR-041**: Limits of a decision. A decision is evidence input, never authorization: apply still requires the existing explicit owner authorization and recovery journal, re-checks the exact tip OID and keeps every protection; recovery is as stated in the design rationale (tip history only, local ref, manual restore). `kind: ai` decisions are marked in the plan and journal so the owner can see which were not human.

### Merged-PR discovery (fixes #81)

- **FR-013**: Online planning discovers merged-PR evidence by head OID with no `--pr` hint for every distinct unproven tip OID. Discovery is read-only GET against one explicitly resolved repository and uses only the closed endpoint set in [PR discovery](contracts/pr-discovery.md#endpoint-set): the repository record, the closed-PR collection (up to 10 pages of 100) and the per-PR read already allowed by Spec 029. No write, redirect to another host or compression (Spec 029 online contract). No second endpoint is added by this Spec.
- **FR-014**: Hints and evidence are keyed by distinct OID. Several refs with the same OID share one hint and one evidence record listing every ref. A repeated identical `--pr OID=N` is idempotent; the same OID with a different number is a usage error naming the OID and both selectors.
- **FR-015**: `--pr OID=N` overrides discovery for that OID only and still passes full tuple validation (Spec 029 FR-007). A hint for an OID no selected ref carries is a usage error naming the OID.
- **FR-016**: Every usage or discovery refusal names the offending selector: full flag text (`--pr <value>`), the OID and affected refs, escaped and truncated to the Spec 029 4,096-byte bound.
- **FR-017**: Discovery coverage is explicit and amends Spec 029's refusal of a full final page without proven exhaustion (amendment 5). Positive evidence stays usable: an exact-head merged PR that is found and passes the full Spec 029 tuple verification and re-read is proof for that OID regardless of collection completeness. Only absence is inconclusive: when the closed collection ends within the page and record bounds, coverage is `complete` and OIDs without a match are `integration-not-proven` with `no-merged-pr`; when a bound is reached, coverage is `incomplete` and OIDs without a found PR are retained `integration-not-proven` with `discovery-incomplete`; the plan does not refuse. Several admissible PRs for one OID need an explicit hint (Spec 029 FR-008).
- **FR-018**: Discovery shares the Spec 029 FR-025 online budget unchanged: one 30-second online plan deadline, at most 128 HTTP requests and 32 MiB raw response bytes per run, shared with tracking-ref reads and counting failures. Request accounting, taken from the baseline source and cited: the plan path costs one repository read when the session opens (`internal/hosting/tidy_evidence_session.go:224`), one repository revalidation at the start of `DiscoverPullRequests` (`internal/hosting/tidy_evidence_pr.go:283`), at most 10 closed-PR pages (`discoverPRHints`, `tidy_evidence_pr.go:209`, `maxPages = 10` at `internal/hosting/transport.go:23`) and one PR read per candidate (`readPullRequest`, `tidy_evidence_pr.go:303`); the total request ceiling is 128 (`tidyMaxRequests`, `tidy_evidence_session.go:20`). Formula: candidate reads fit = (128 - fixed repository reads - page reads) / cost per candidate = (128 - 2 - 10) / 1 = 116 with all ten pages read; with fewer pages more fit. The cost is per candidate PR, not per OID: an OID with two candidate PRs costs two reads. The two-request pair (repository revalidation plus PR read) is `RevalidatePullRequest` (`tidy_evidence_pr.go:159-173`), which runs at apply, inside the apply run's own budget and outside this plan budget; a literal reading of the Spec 029 online contract (online.md "re-read repository ID with it") would make it three per PR, but the source is the baseline and T022 asserts the exact counts against it. Re-reads proceed in ascending OID order; when the remaining budget cannot cover the next candidate PR read, that OID and all later ones are `integration-not-proven` with `discovery-budget-exhausted` and the plan completes with a note. The 60-second forge-free proof phase (FR-008) runs first as its own phase; the online phase keeps its own 30 seconds, so the sequential totals are those of FR-008. T021 measures why #81 needed hints; a second endpoint is out of scope and revisited only on that evidence in a later amendment.

### Configuration policy (fixes #79)

- **FR-019**: Planning commands (observation, reads and proofs) run with the sanitized environment and one constant argument list shared by planning and apply re-evaluation: no inherited `GIT_*` override, including `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_*`/`GIT_CONFIG_VALUE_*`; every native command of the proofs and the report additionally runs with a private empty `HOME` and `XDG_CONFIG_HOME` (temporary directories owned by the process, removed afterwards), `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` set to the platform null file (`/dev/null`), `GIT_CONFIG_NOSYSTEM=1` and `GIT_ATTR_NOSYSTEM=1` (so no global, XDG or system configuration or attributes file applies); `-c core.hooksPath=/dev/null -c core.fsmonitor=false -c submodule.recurse=false -c core.untrackedCache=false -c merge.renormalize=false -c merge.renames=true -c merge.directoryRenames=conflict -c merge.renameLimit=1000 -c diff.renames=true -c diff.renameLimit=1000 -c core.autocrlf=false -c gc.auto=0 -c maintenance.auto=false -c protocol.ext.allow=never`, `--no-optional-locks`, `--no-replace-objects`, `GIT_NO_LAZY_FETCH=1`. A separate admission read lists effective configuration with origins (global and system included) for classification and plan notes; it executes no helper.
- **FR-020**: Classification ([policy](contracts/configuration-policy.md)). **Neutralized for planning** (recorded plan note, plan succeeds): `core.hooksPath`, `core.fsmonitor`, `submodule.*`, `core.pager`, `core.editor`, `core.sshCommand`, `core.askPass`, `credential.*`, `gpg.*`, `diff.external`, `diff.<driver>.textconv`. **Review reasons for a proof only** (plan still succeeds, FR-010a): `merge.*.driver`, executable `filter.*` (`merge-driver`), merge attributes (`merge-attribute`), `info/attributes` (`attribute-source`), `diff` attributes (`diff-attribute`); **hard stops** for every proof: grafts, shallow (`history-override`), alternates (`unsupported-metadata`). **Refused, no plan** (class `git-unsafe-configuration` or the existing Spec 029 class, unchanged): `hook.*`, `include.*` only as `includeIf.*`, `core.attributesFile`, `extensions.worktreeConfig`, `extensions.partialclone`, `remote.*.promisor`, `core.alternateRefsCommand`, `core.sparseCheckout*`, and the reserved sentinel `filter.unspecified|unset|set.*` names. Plain `include.path` is evaluated by Git and classified by effective keys. Whatever stage2 does today for other executable `filter.*` in the safety collector stays (T002 confirms). Unknown executable-looking keys are refused by class.
- **FR-021**: Justification and unchanged items. Only `core.hooksPath`, `core.fsmonitor` and `submodule.*` change from refused to neutralized: no read-only planning command runs hooks, fsmonitor or `git submodule`, and the arguments of FR-019 disable them on every command; this is the precedent already used for inventory and release reads. `hook.*` stays refused because command-line `core.hooksPath` does not neutralize config-based hooks; `core.attributesFile` stays refused because it changes content evaluation. The default `.git/hooks` fingerprint remains bound into the safety digest unchanged: a changed or executable hook changes the plan and apply refuses a hook-running effect. Gitlinks are data: no `git submodule`, no descent by this Spec's commands; `merge-noop` gets review reason `gitlink-change` when a gitlink differs (FR-004). A worktree retirement target with an initialized submodule retains `submodule-present`.
- **FR-022**: Apply keeps every existing refusal. Neutralization is planning-only: the plan records the neutralized configuration digest and a per-plan `apply_effect`; apply refuses effects whose hooks or helpers would execute (for example a `reference-transaction` hook for a ref deletion), naming the class, never skipping hooks silently.
- **FR-023**: Sentinel test for every class: a configured helper writes a marker file; the marker is absent after planning; plan notes or refusals name the class. Mutants (remove a `-c` item, inherit `GIT_CONFIG_PARAMETERS`/`GIT_CONFIG_COUNT`, inherit global config) must fail the matrix.

### Bounded planning (fixes #80)

- **FR-024**: The v1 and v3 reference and registration reads stream through the existing bounded native stream executor, parsing record by record; whole-output buffering at 64 KiB (`nativeOutputLimit`) no longer applies to `for-each-ref` and `worktree list --porcelain -z`. Memory is bounded by one record plus the parsed set.
- **FR-025**: Hard bounds remain refusals (*proposed*, Spec 029 constants): at most 1,024 references and 1,024 registrations (`observationLimit`); each record at most 4,224 bytes; each stream at most 4,325,376 stdout and 65,536 stderr bytes. One record or byte over refuses with `git-observation-limit` or `git-output-limit` naming the stream, never a truncated plan.
- **FR-026**: v3-only documentation is not chosen; v1 is repaired so v1/v2 callers keep working with unchanged published bytes and result shape. 64 KiB stays for non-collection reads.

### Acceptance and effects

- **FR-027**: Acceptance: a plan-only source test runner (in-process, no build) plans this repository and the Anchorage umbrella read-only with a temporary state directory, private object directory and an owner-named temporary report directory, never `apply`, and records counts before (stage2 baseline) and after per bucket (deletable by proof, needs-review by reason, retained), attaches generated report samples, and runs a documented manual acceptance step in which an AI reviewer (a Claude subagent) evaluates the JSON report for N branches and a human spot-checks the verdicts. A CLI-binary lane needs a separately named owner build authorization; without it that lane is a recorded gap.
- **FR-028**: Every behavior is first covered by failing tests using temporary repositories, golden Markdown and JSON fixtures and deterministic transport doubles (constitution IV); no test touches a real user repository except the read-only acceptance runner of FR-027.
- **FR-029**: Schema: additions are additive to the unpublished v3 result and plan; the report JSON and decision file have candidate schemas in [data model](data-model.md); v1/v2 schemas and fixtures stay byte-identical; v3 is published only with accepted implementation.
- **FR-030**: No new network write, remote ref effect or repository write effect; proof and report commands write only to their private temporary object directory, and the report only to the owner-named directory (FR-032).

## Known limits

Residual low-probability risks are documented here instead of becoming rules: patch equivalence does not show that a change is still present on the base (labelled, recoverable); a diff can contain secrets from the branch (report files are 0600 and sensitive); the unintegrated diff of a conflicting merge contains conflict markers; unobserved concurrent changes during planning (Spec 029 ABA qualification); attribute sources other than the pinned tree are covered only by the blanket reasons of FR-010a; Git behaviour was measured on 2.47.3 and 2.56.0 only; the recovery ref preserves the tip history only (design rationale); a reviewer, human or AI, can be wrong, which is why a decision is bounded by the exact tip OID and never authorizes apply.

## Owner-gated work

Not permitted without explicit owner authorization naming the one operation (workspace `AGENTS.md`): building or installing a CLI artifact, running a built `stw`, `apply` against any real repository, tag, release, publication, repository/ruleset settings, merge, consumer image activation. Source tests, formatting, vet and test-compiler verification may run automatically. A reviewer decision, human or AI, is never an authorization. The defaults above (git patch-id as default proof, `--accept-whitespace-differences` opt-in, the bounds, the separate forge-free phase, the report bounds) are decisions revisable by the owner.

## Key entities

- Proof evidence: class, strength, base selector/OID, tip OID, counts, policy version, disposition (`proven`, `needs-review`, `retained`), reasons.
- Review report entry: reasons, commits, proofs tried, unintegrated diff, candidates, range pairing, suggested verdict, questions.
- Decision: branch, tip OID, decision, reason, reviewer, kind.
- Discovery record: OID, hint number and identities, covered refs, coverage (`complete`, `incomplete`), source (`discovered`, `hint`).
- Configuration note: key class, neutralized or refused, digest, effect on apply.

## Assumptions and scope

Same-user cooperative repositories (Spec 029). Native Git minimum/current lanes as Spec 029 (2.46.0 / 2.56.0); `merge-tree --write-tree` requires Git 2.38+ and `--attr-source` 2.40+. jj and GitButler backends are out of scope. `merge-noop` proves present content; patch equivalence proves that an equal change existed on the base at some point, not that it is still present; the plan labels it and recovery bounds the risk. Consolidated work is retained unless a reviewer decision clears it.
