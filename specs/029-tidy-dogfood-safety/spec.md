# Feature Specification: Complete local tidy with explicit integration evidence

**Feature Branch**: `codex/tidy-dogfood-contract`
**Created**: 2026-10-18
**Status**: Stacked-integration amendment awaiting exact specification/plan re-review; prior specification `99539328` and plan `5272dc1e` were independently CLEAR. No implementation acceptance.
**Input**: User request: "this fix findings, then rerun tidy and analyze result again". The selected findings are rewritten PR integration, completed legacy attached worktrees, the base-tree metadata limit, and stale local remote-tracking references.

## User Scenarios & Testing

### User Story 1 — Recognize exactly merged work after history rewriting (Priority: P1)

An operator explicitly enables online evidence and reviews local branches whose original commits were merged through GitHub rebase or squash. Ordinary offline tidy remains useful without a forge or authentication.

**Why this priority**: Native ancestry alone cannot identify the original head after the repository's normal rebase-merge workflow.

**Independent Test**: Temporary repositories and deterministic provider responses contain merged original heads, rewritten integrated commits, reused names, divergent bases and active worktrees. Online and offline plans produce their declared decisions without native mutation.

**Acceptance Scenarios**:

1. **Given** an exact local tip matching a merged PR head and the PR's integration commit reachable from the explicitly chosen base, **When** online tidy discovers the PR and validates all other guards, **Then** it proposes deletion with provider evidence and recovery requirements, even when original-head ancestry is false.
2. **Given** no online selection, **When** the same plan runs, **Then** it makes zero network/authentication calls and retains the unsupported rewritten head with its existing reason.
3. **Given** an amended local tip, a reused branch name, an unmerged/closed PR, a wrong repository or an integration result not reachable from the chosen base, **When** evidence is evaluated, **Then** no name, merged label or patch-equivalent result substitutes for the exact head and target proof.
4. **Given** ambiguous, unavailable, truncated or changed provider evidence, **When** planning or application runs, **Then** affected targets retain or refuse before their next effect, with an incomplete result when observation failed.
5. **Given** a merged target still used by any registered worktree, **When** reference tidy runs, **Then** it remains protected until a separately selected retirement completes and a new reference plan is generated.
6. **Given** an exact merged head whose PR targeted an intermediate stack branch, **When** its provider-reported integration commit is present locally and reachable from the chosen base, **Then** it can qualify even if that intermediate branch is now deleted or renamed; the observed PR base name/SHA remain bound and freshly compared, and no recursive PR-chain or patch-similarity inference is used.

### User Story 2 — Retire explicitly completed legacy worktrees (Priority: P1)

An operator selects an old manually created, branch-attached Git worktree, explicitly declares that its task is complete and no user or agent is using it, reviews exact removal effects, and retires it without pretending it was created by SourceSteward.

**Why this priority**: Existing task-journal-only, detached-worktree retirement cannot handle completed manual worktrees. A registration alone does not mean active work forever; neither does a merged PR establish permission to remove it.

**Independent Test**: Temporary repositories model six clean, merged, attached legacy worktrees with 315–358 tracked files each, including a 301,117-byte SVG, alongside an active task and a dirty primary checkout. Explicitly completed selections can retire; every other workspace and file is preserved.

**Acceptance Scenarios**:

1. **Given** an explicitly completed, selected legacy worktree with exact native/physical ownership, full clean tracked/staged/untracked/ignored evidence and proven integration, **When** both registration and exact-path file removal are planned and authorized, **Then** retirement records its legacy provenance and recovery, removes only that worktree, and leaves its branch for a fresh reference-tidy plan.
2. **Given** an unselected, currently used, protected, locked, primary, foreign, dirty or incompletely observed worktree, **When** retirement is requested, **Then** it retains with the precise blocker; completion intent cannot override a blocker.
3. **Given** a missing original creation journal, **When** a legacy completion plan is prepared, **Then** the operator's explicit one-operation claim is recorded as new evidence, never a fabricated historical creation journal or standing ownership claim.
4. **Given** a newly written tracked, untracked or ignored file, a replaced path, moved HEAD, attached-branch change or changed protection input after planning, **When** apply revalidates, **Then** the next destructive action refuses and any recovery already created remains reported.
5. **Given** a legacy worktree with ignored caches or any other extra content, **When** full retirement is requested, **Then** it retains; the command neither deletes those extras nor silently detaches, stashes or resets it.
6. **Given** 315–358 tracked files including the 301,117-byte SVG, **When** the new Git retirement content capability observes all stored/index/disk evidence, **Then** it proves complete clean content within its byte/process/time budgets and can retire an explicitly completed target; the old 64 KiB stored/disk file limit cannot silently remain in this path.
7. **Given** a stream ends early, emits an extra byte, reports a wrong object/size, exceeds its budget or stalls, or an actor changes content/mode/link/path identity during or after hashing, **When** a fresh observation or deletion-adjacent check runs, **Then** it refuses before removal and retains any already prepared recovery. Same-size edits and restored modification times are included.

### User Story 3 — Inspect an admitted base beyond 64 KiB of metadata (Priority: P1)

An operator can plan against an ordinary selected base whose complete tree fits the established entry and file-content bounds but has more than 64 KiB of path metadata.

**Why this priority**: The current repository's current base fails before branch proof begins. Selecting fewer branch refs cannot reduce the base-wide safety inspection.

**Independent Test**: Temporary bases straddle the old byte limit and every new byte/record bound, including long paths and unsafe final entries. Run creation, reference tidy and retirement consumers of the shared admission contract.

**Acceptance Scenarios**:

1. **Given** 695 ordinary files with 67,877 bytes of tree metadata, **When** all existing path, blob, attribute and safety guards pass, **Then** full-base planning succeeds rather than failing at the old 64 KiB total-output limit.
2. **Given** the last entry is unsafe, an active filter applies only to the last path, or output ends mid-record, **When** the bounded inspection runs, **Then** it refuses; streaming never permits a prefix to authorize mutation.
3. **Given** a bound is exceeded or evidence changes between samples, **When** any shared consumer runs, **Then** it refuses with the named bound or stale reason and preserves all undeclared state.

### User Story 4 — Remove stale local tracking refs without remote deletion (Priority: P1)

An operator explicitly selects online tracking-reference cleanup for one configured remote, reviews which local tracking refs have no corresponding branch in a complete provider advertisement, and applies only those local effects.

**Why this priority**: Stale tracking refs and merged local branches are distinct objects and need distinct evidence and recovery.

**Independent Test**: Temporary local namespaces and provider branch advertisements reproduce one and three stale tracking refs, live branches, symbolic remote HEAD and changed mappings.

**Acceptance Scenarios**:

1. **Given** a local tracking ref with a unique admitted mapping and complete repeated remote branch evidence showing its source absent, **When** online tracking cleanup is explicitly selected and authorized, **Then** it preserves the old local OID in recovery and removes only the exact local tracking ref with an old-OID condition.
2. **Given** a corresponding remote branch exists, including at a different OID, **When** cleanup plans, **Then** it retains the tracking ref; this feature does not synchronize it.
3. **Given** symbolic remote HEAD, its target, the selected base, unsupported mappings, incomplete advertisement or repository/configuration changes, **When** cleanup evaluates or applies, **Then** it retains/refuses and never infers absence from an error.
4. **Given** the remote branch reappears before final validation or the local tracking ref moves, **When** apply runs, **Then** deletion refuses; no fetch, server deletion, configuration repair or generic prune fallback occurs.

### Edge Cases

- Force-push/rebase, multiple exact-head PRs, renamed/transferred repositories, deleted head repositories, forks, merge queues, permission loss, rate limits and cancellation.
- Current/source/primary workspace protection, overlapping parent/child paths, native locks, linked metadata replacement, attached branch reused after retirement, ignored files and special filesystem nodes.
- Empty trees, boundary-length paths, SHA formats, malformed final metadata, filter sentinels, hidden helper invocation, interrupted recovery and partially completed batches.
- Remote refspec duplication/negation/overlap, multiple fetch URLs, URL rewrites, symbolic chains, custom tracking namespaces, same repository under ambiguous host identities and branch recreation between observations.

## Requirements

### Common contract

- **FR-001**: Preserve the existing offline commands and their zero-network effects. Online evidence requires explicit `--online` selection for planning and explicit online-effect acknowledgment at apply. A stored online plan alone does not enable networking; `--authorize` still separately acknowledges its listed local effects.
- **FR-002**: Every plan identifies the backend, exact base selector/OID, scope, targets, reasons, completeness, relevant identities, online effects and local effects. New proof/action fields use a new versioned tidy contract; published v1/v2 bytes and old-plan meaning remain unchanged. Human and structured output derive from the same observations.
- **FR-003**: Keep inspectable immutable plans, private state integrity, pre-action durable recovery, per-action stale validation, partial outcomes and bounded retry. A changed plan or relevant state requires replanning. No successful prefix of an incomplete observation authorizes a candidate. Complete negative observations retain with exit 0; unavailable/unknown/stale evidence gives exit 1; malformed invocation gives exit 2.
- **FR-004**: Preserve native ownership selection, supported-version checks, admitted checkout layouts, executable identity, sandbox grants, helper/configuration/attribute safeguards and complete registered-workspace protection. Native mutation remains network-denied; hosting reads have a separate explicitly disclosed boundary. No unsandboxed or raw-Git fallback for jj/GitButler ownership.
- **FR-005**: Initial new online and legacy capabilities support admitted native Git and GitHub.com repositories. Fork PRs, unsupported host/provider/object-format combinations and ambiguous identities retain explicitly. Existing native jj tidy/retirement remains supported under its existing contracts and regression lanes; these new capabilities are not presented as jj parity.

### Online integration evidence

- **FR-006**: Online plans support bounded automatic discovery of exact-head PR candidates for selected local refs, plus optional explicit PR-number hints. Discovery is scoped to one explicitly resolved provider repository, without filtering by original PR base name, never a global search. PR-number hints narrow discovery but do not bypass any proof. Branch names only discover candidates; they are never proof.
- **FR-007**: Provider proof requires a complete authoritative PR observation with merged status, stable repository and PR identifiers, exact local tip equal to the PR head OID, matching admitted head/base repositories, and the provider's integration commit present locally and reachable from the exact chosen base OID. Bind the observed PR base name and SHA separately; neither must equal the chosen base selector/OID. This permits integration through an intermediate stack branch only when that same reported integration commit has native ancestry into the chosen base; no inferred PR chain replaces ancestry. Ordinary merge, squash and rebase use the same exact-head attribution rule. Patch equivalence alone never authorizes cleanup.
- **FR-008**: Re-read each chosen PR's complete identity and merge facts after discovery and at application boundaries. Multiple admissible PRs require an explicit selection; inconsistent identities, changed head/base/merge facts or missing stable IDs retain/refuse. Discovery exhaustion proves only that no supported match was found. Provider fields are trusted sampled assertions, not a guarantee of historical immutability or an external transaction.
- **FR-009**: Select the host explicitly or use the existing fixed default; repository text cannot redirect credentials. Bind host, canonical provider repository ID, configured local remote identity when used, exact PR ID/number, head/base identities and integration commit into plan integrity. Re-read repository identity to detect name reuse/transfer. Authentication and HTTP errors, redirects, compressed/malformed/oversized responses, incomplete pagination and cancellation fail closed; no anonymous retry, cache-as-authority, credential setup or fetch fallback.
- **FR-010**: Retain selected bases, symbolic refs, registered-workspace-used refs and uncertain targets regardless of integration proof. Refresh provider proof and native state before recovery preparation and again before each destructive action after recovery confirmation. A provider failure after recovery creation preserves and reports that recovery. No stale cached proof is accepted by age alone.

### Explicit legacy completion and retirement

- **FR-011**: Add a distinct legacy-completion plan mode selecting one exact absolute worktree path, one owner label and an explicit operator declaration of task completion and exclusive retirement authority. The caller must declare that no human/agent is using it and supply all known active workspace protections. The declaration is a cooperative trust input, not authentication, process detection or evidence of historical stw creation; absent declaration retains. It grants no standing adoption or authority over another path.
- **FR-012**: Bind the completion claim to canonical repository/common-directory/per-worktree identities, reciprocal native pointers, filesystem owner and physical destination/parent identities, exact HEAD OID and attached local branch when present, full registration set, protection set and full clean-content/metadata manifests. Admit same-user linked Git worktrees of the same repository only. Refuse primary, current working directory or ancestor, source, caller-protected or known-active paths, foreign backend/OS ownership, path aliases/overlap, native worktree/index/HEAD/ref locks, ongoing native operations and incomplete evidence. Completion intent cannot override these blockers. A mere registration is not an active-task assertion.
- **FR-013**: The selected legacy path must have complete fresh tracked, staged, untracked and ignored evidence with no changes or extra content, and full stored-tree/disk equality under retirement's supported node/path/content bounds. Inventory `clean=true` alone is insufficient when it omits needed scope or only lists a bounded prefix. Preserve the existing physical manifest and metadata safety requirements; the new Git v3 user-content byte limits are the explicit exception defined by FR-029–FR-032 below. Unknown, inaccessible, special, dirty or extra nodes retain.
- **FR-014**: Support attached legacy branches as well as detached legacy heads when the exact target HEAD has admitted integration proof. A legacy completion record is explicitly labeled with its own provenance; never forge a completed creation journal or acquire/overwrite another task's lock. Existing stw-owned retirement retains its separate original-journal verification.
- **FR-015**: Require separate selected registration and exact-file-removal effects. Native Git's combined worktree removal requires both; no registration-only forget of a present checkout. Record and confirm a recovery root for the exact target commit before removal, retain the local branch, and preserve siblings and primary/source state. Retirement does not implicitly authorize branch deletion. Subsequent reference tidy must use a fresh plan and fresh provider evidence after registration removal.
- **FR-016**: Revalidate completion/protection inputs, HEAD/branch, physical identity, clean manifests, metadata and repository identity before each effect and verify postconditions. Report partial registration/file outcomes without automatic cleanup, adoption or retry. Recovery preserves the selected committed history, not arbitrary untracked files, original index/reflog/configuration or a promise of automatic worktree restoration.

### Complete bounded tree admission

- **FR-017**: (The leaf bound is 16,384 for the tree and filter channels after the [creation refusals amendment](../010-isolated-task-workspaces/contracts/workspace.md#creation-refusals-amendment), shared by creation, tidy and retirement; there it only bounds cost, since streams are all-or-refuse. The deletion-deciding limits keep their values: raw user-blob sample 1,024 files, manifest 1,024 entries, 64 MiB total.) Replace the shared workspace safety collector's whole-output 64 KiB limit only for complete base-tree metadata and its all-path filter evidence with bounded record consumption. Retain the independent 16,384-leaf, 4,096-byte path, 16 MiB per-blob and 64 MiB total-blob limits. Apply the new metadata contract consistently to creation, reference tidy and both retirement modes, including target-tree checks; reference selection never bypasses the full selected-base check.
- **FR-018**: Each logical tree or path/filter record is at most 4,224 bytes, including delimiters; each complete tree or complete all-path filter observation is at most 4,325,376 stdout bytes (the byte bound of the original 1,024-leaf design, kept unchanged when the leaf count became 16,384: an average of about 264 bytes per entry at the cap), with at most 65,536 stderr bytes. A record allowance is the existing 4,096-byte path plus 128 bytes for validated fixed metadata. All other native outputs keep their current bounds. Exactly-at-limit valid input is admitted; the first detection byte/entry over any limit refuses. No truncated success, allocation proportional to unchecked input or unlimited drain is allowed.
- **FR-019**: Validate every record/path/object/size and every path's attributes, including the final entry. Include complete validated tree and attribute evidence and existing layout/config/helper/executable evidence in deterministic safety fingerprints; sample again at existing stale boundaries. Preserve no-helper/no-network guarantees and cancellation/child-reaping obligations. This is not adoption of inventory's helper-neutralizing runner or its partial-listing semantics.

### Complete bounded retirement content

- **FR-029**: New Git tidy schema v3 retirement, both explicit legacy completion and stw-owned retirement selected under that version, supports regular stored user files up to 16 MiB each and 64 MiB total user content per complete tree/sample, matching existing Git checkout content bounds. This is separate from FR-017–FR-019 metadata parsing. Retain at most 1,024 aggregate manifest/observation entries and 1 MiB encoded records. Apply the versioned content policy consistently to stored facts, physical manifests, recorded-plan validation and every revalidation boundary; never raise a shared constant and silently broaden old v2 or native jj retirement. Git/jj v2 retain their 64 KiB raw-file limit. Native metadata files, including the worktree pointer and registration/index/reflog metadata, remain at most 64 KiB each.
- **FR-030**: Read raw stored content and physical disk content incrementally in at most 64 KiB buffers; preserve binary bytes and compare complete SHA-256 content digests, exact lengths and executable/mode facts. A stored stream must match the requested full object identities, blob type and admitted size; enforce exactly that many content bytes, expected framing and final EOF, rejecting missing/extra data and unsuccessful process exit. No text conversion, filters, helper, lazy fetch or newline normalization. Bound each complete stored-content stream to 64 MiB payload plus 128 KiB framing (1,024 × 128 bytes), and stderr to 64 KiB; use at most one native raw-object process per full stored-content sample, with no subprocess per file. Input object identities and framing are separately bounded and validated. Cancellation must stop and reap the process without an unbounded drain or stderr allocation.
- **FR-031**: Each disk-content pass uses confined no-follow regular-file opens, rejects hardlinks/special nodes, and checks the path and open descriptor's device/inode, type, mode, link count, exact size, modification time and change time before/after the complete hash and again at the deletion-adjacent sample. A missing required identity/time capability refuses the new content capability. Read exactly the admitted size and test EOF; early EOF, growth, digest mismatch or any observable metadata/path change refuses. Include these facts in the versioned manifest and stale comparison. Modification/change timestamps do not replace hashes and cannot exclude timestamp-granularity/ABA races; retain that limitation explicitly. Extra/untracked/ignored paths remain refusal conditions, regardless of size.
- **FR-032**: Budget every proof read, including repeated reads, against the following one-operation ceilings without resetting counters per file or resample. The existing guard placement requires three full observations in planning and eight in apply. Each full observation permits one stored-user pass, two disk-user passes and two passes of each physical and registration metadata manifest. Thus user-content reads are at most 9 × 64 MiB = 576 MiB for planning and 24 × 64 MiB = 1,536 MiB for apply; raw-object process counts are at most three/eight. Each registration-metadata pass remains bounded by 1,024 entries × 64 KiB = 64 MiB (a conservative ceiling before the shared aggregate-entry check); physical Git metadata is only the admitted `.git` pointer, at most 64 KiB per pass. Two passes of each therefore add at most 128 MiB + 128 KiB per full observation. Total content-proof bytes, including all user/metadata resampling plus native framing/stderr, are at most 3 × (320 MiB + 320 KiB) for planning and 8 × (320 MiB + 320 KiB) for apply. These are consumption ceilings, not allocated buffers or a promise every maximum-size tree finishes. A changed design requiring additional passes must fit a reviewed budget, never omit a safety check to finish. Planning has a 60-second total offline deadline (90 seconds online; amended from a fixed 10 and 30 seconds that a loaded runner or a thousand-file repository could exceed); each full native observation has a 60-second context, and the complete apply retains 60 seconds, all subordinate to the original caller context. Budget/deadline exhaustion before removal refuses, including after recovery creation. Git's combined native removal has no additional SourceSteward user-file unlink pass: final full observations are its deletion-adjacent checks; native internal I/O is bounded by its sandbox and remaining deadline, not falsely claimed to be measured by the proof-stream byte counter. Native jj/shared per-entry unlink behavior remains v2 and unchanged.

### Stale local tracking-reference cleanup

- **FR-020**: Add explicitly selected online tracking-ref planning for one named configured remote. It is distinct from local branch selection and legacy retirement. Only direct local refs under that remote's `refs/remotes/REMOTE/` namespace are candidates; no server branch, tag, local branch, other remote namespace or provider setting is mutated.
- **FR-021**: Initial admission requires one fetch URL identifying the selected GitHub repository and exactly one standard full-head mapping `+refs/heads/*:refs/remotes/REMOTE/*` (the optional leading `+` does not change namespace identity). Refuse duplicate, negative, overlapping, mirror or custom mappings, multiple URLs, URL-rewrite ambiguity and unresolved configuration origins. Bind complete relevant config bytes/origins, selected remote identity and canonical provider repository ID; configuration is never rewritten.
- **FR-022**: Prove source absence from a complete unfiltered provider branch advertisement for that exact repository, not a single-branch 404, PR state or stale local tracking data. Collect and compare two complete advertisements while planning and re-observe complete advertisement/config/repository identity at apply boundaries. Duplicate/malformed names, changed page data, unproven exhaustion, missing permission, redirects or budget exhaustion retain/refuse. The provider branch inventory is the declared remote evidence; no Git fetch or native remote-transport helper is introduced.
- **FR-023**: Retain symbolic tracking refs, every resolved symbolic-HEAD target, the chosen base/OID and any ref protected by current workspace evidence. An existing remote source retains even when its OID differs. Delete only after absence is freshly confirmed and exact direct local ref identity still matches, using an old-OID condition and no symbolic dereference; verify absence and durable recovery after the effect. Any local symbolic transition refuses, never follows the referent.
- **FR-024**: Explicitly disclose that advertised remote absence is sampled and cannot prevent a branch being recreated immediately afterward. Preserve recovery for the deleted local tracking OID. This action does not establish branch integration, remove local branches or promise remote synchronization.

### Bounds, effects and acceptance

- **FR-025**: Online planning has one 30-second total deadline; apply keeps one 60-second total deadline; native reads retain their tighter deadline. Each raw and normalized HTTP response and encoded stored/result record is at most 1 MiB; each authentication stdout/stderr buffer remains at most 16 KiB. One online run permits at most 128 HTTP requests and 32 MiB total raw response bytes, including errors and repeated observations. Collections permit at most 10 pages, 100 rows per page and 1,000 unique records, with explicit exhaustion; 1,000 records without proven exhaustion is incomplete. Total candidate/workspace observations retain the existing 1,024 bound. Requests/detection bytes count even on failure; bounds cannot be reset per candidate. Narrow selections are available when a complete plan cannot fit.
- **FR-026**: All new effect classes are visible before apply: host-specific authenticated reads, private plan/completion/recovery records, native recovery roots, exact local-ref deletion, or exact legacy registration/files removal. No server writes/deletes, fetch/prune, GC, automatic activation, environment/configuration changes, stash/reset, branch switching/detachment, hooks, arbitrary helpers or fallback cleanup.
- **FR-027**: Plans and recovery records bind the proof policy/version, native state, precise action authority and provider/legacy/mapping evidence relevant to each effect. Do not store tokens or unrelated API text. Preserve effect boundaries on interrupted batches: already completed actions remain reported, later actions stop when their prerequisites are invalid. Retried completed actions verify recorded postconditions without repeating removal.
- **FR-028**: Before implementation, review this specification, then a plan, tasks and cross-artifact consistency/security analysis under the installed Spec Kit gates. Implement behavior test-first using temporary repositories and provider fixtures. Require minimum/current Git conformance, existing jj regressions, source checks, independent exact-head review and recorded acceptance. Live two-repository reruns use only reviewed stw plans/applies after a separately approved candidate build/install; absent build approval is not permission for raw cleanup.

### Key Entities

- Integration evidence: provider/repository/PR stable identities, exact head, selected local base selector/OID and observed PR base, merge result and completeness/freshness.
- Legacy completion claim: exact selected workspace and operator authority declaration, protection set, physical/native identity and clean manifests; distinct from original stw ownership.
- Tracking mapping and advertisement: local remote/config identity, mapped source/destination refs, complete observed remote branches and observation bounds.
- Cleanup plan/action: immutable exact targets, reasons, relevant evidence, intended effects, per-action outcomes and durable recovery references.

## Success Criteria

- **SC-001**: Rewritten exact-head fixture candidates, including seven intermediate-base cases among nine merged-head candidates, become eligible online while their offline counterparts retain; every mismatched, ambiguous or unavailable evidence case retains/refuses. All unselected and workspace-used refs remain intact.
- **SC-002**: Six realistic fixtures with 315–358 tracked files each and a 301,117-byte SVG, including intermediate-base merged PRs whose reported integration commits reach the selected base, retire when explicitly selected and authorized, then a fresh plan can remove their integrated local branches. Each fixture has complete tracked/staged/untracked/ignored evidence; verification records maximum buffer size, full bytes/pass counts, native raw-object process count and elapsed planning/apply time under FR-029–FR-032. A one-file surrogate is insufficient. Valid fixtures exactly at 16 MiB per user file and 64 MiB total are admitted when every other guard, byte/process budget and FR-032 deadline passes; this is not a promise that every maximum-size tree finishes within the deadline. Over-limit fixtures, short/extra/stalled streams, same-size actor writes with restored mtime, late edits, mode/link changes and symlink/path replacement must refuse without removing user data. Active/protected worktrees and a primary checkout with an untracked document and ignored cache remain byte-preserved.
- **SC-003**: The 695-entry/67,877-byte fixture and valid maximum-bound cases pass full inspection; every one-unit overrun, unsafe final record and changed-evidence case refuses without undeclared effects.
- **SC-004**: Fixtures with one and three stale tracking refs remove exactly those authorized local refs; existing remote heads, symbolic refs/targets, chosen bases and unrelated namespaces remain unchanged. No provider mutation occurs.
- **SC-005**: Every published-contract regression validates; every new complete/retained/error/partial result validates against the new contract and agrees with human output. Missing mandatory native execution is reported as a gap, never a pass.
- **SC-006**: After authorized candidate activation, rerun each real repository against the explicitly chosen current integration base, report original versus fresh counts separately for local refs, worktrees and tracking refs, and explain every retention/partial effect with recovery pointers. Do not promise a majority deletion independent of current state, explicit selections or safety evidence.

## Assumptions and scope

The operator controls a cooperative same-user repository and explicitly coordinates completed versus active work. Filesystem permission is necessary but does not prove activity or historical ownership. Concurrent external/ABA changes remain outside a transaction guarantee; every observable relevant change refuses. The six supplied legacy examples were clean across tracked/staged/untracked/ignored scopes, but all contain a 301,117-byte SVG that exceeds the existing 64 KiB retirement stored/disk limit. Their 315–358 blobs and 29,436–33,748 metadata bytes fit the old tree-metadata limit. Both the separate user-content amendment and legacy-completion authority are required; the base-tree metadata fix alone cannot satisfy SC-002. Seven of nine merged-head SheetMill examples originally targeted intermediate stack branches; exact reported integration-result ancestry into the selected base is required, rather than original PR base-name equality. Those observations are motivation, not reusable apply authorization.

The four selected feature fixes authorize design/source work. This specification is not a cleanup plan or build/release authorization. Existing source and native safety contracts remain binding except for the precise proposed amendments in [contract amendments](contract-amendments.md). Spec 027 changes inventory only and does not authorize mutation-boundary reuse. Spec 028 and unrelated release work remain outside this feature.

Full legacy retirement is selected for the initial scope because it addresses the measured clean attached worktrees with exact existing manifest/recovery protections. Same-commit detachment would introduce a separate HEAD mutation, hook/index and recovery contract; it is deferred, not used as a silent fallback when extra files block retirement. No bulk automatic adoption or filesystem deletion from PR status alone.

The provider is trusted to attribute a merged PR's exact reported head to its reported integration commit. Stable identities, repeated observations and reachability checks bind that assertion to the local target and chosen base; patch similarity is optional supporting information only. Fork support, other providers/hosts and larger online inventories require separately specified acceptance.
