# Proposed contract amendments for Spec 029

Status: proposal for the specification gate, not an implemented change. [Spec 029](spec.md) owns the proposed requirements. Existing Specs 010/011 and published v1/v2 schemas remain the runtime contract until reviewed implementation and acceptance. No other specification is implicitly broadened.

## Spec 010: workspace admission and ownership

1. Amend `contracts/workspace.md`, "Preconditions and bounded execution" and "Sandbox limitation": replace the whole-output 64 KiB tree-metadata cap only for complete tree and all-path filter observations with FR-017–FR-019. The new stdout ceiling is 4,325,376 bytes per complete observation, a logical record is at most 4,224 bytes, stderr remains 64 KiB. Retain 1,024 leaves, 4,096-byte paths, 16 MiB/file, 64 MiB blobs, other native caps, safety rules, deadlines and exact stale fingerprints. The 128-byte allowance covers validated mode/type/OID/decimal-size/delimiter overhead (including 64-hex OIDs); an admitted filter result uses only its validated sentinel, not an arbitrary driver value. Both channels retain the 4,096-byte path bound and visit at most 1,024 paths. This is a scope-specific bound change, not a generic runner limit increase.
2. Add a reference from Spec 010 FR-004/FR-007 and handoff/retirement preparation to Spec 029's separately selected legacy-completion claim. Creation records continue to mean actual stw creation. No foreign workspace is adopted by retry, path/name, native registration or owner-label inference.
3. Retain original-journal verification for existing stw-owned retirement. Legacy completion has independent provenance, exact physical/native evidence and one-operation authority. It never fabricates the creation identity or changes creation's detached-worktree behavior.

## Spec 011: reference proof and local effects

1. Amend `spec.md` unsupported forge/squash scope and `contracts/tidy.md` no-network sentence only for explicit online invocations under FR-006–FR-010. Default invocations remain offline. Existing FR-002/FR-003 become implemented only for the admitted provider rule after acceptance; ancestry, provider attribution and patch similarity remain distinct.
2. Add separately selected legacy-completion retirement under FR-011–FR-016, including attached branches. Preserve FR-004's active/dirty/untracked/foreign retention. A native registration is reference-use evidence; activity is not inferred indefinitely from that registration, and the operator's exact completion declaration cannot override known active/protected/current/locked/foreign or dirty state. Existing owned-retirement v2 behavior is unchanged.
3. Add separately selected local tracking-ref cleanup under FR-020–FR-024. Existing remote-reference exclusion continues for server refs and unselected namespaces. Precisely distinguish a local `refs/remotes/REMOTE/...` deletion from a provider branch deletion or fetch/prune; the latter remain excluded.
4. Add the online bounds/effects of FR-025–FR-027. Bind fresh provider observations to application without granting network access to native processes. New online plan effects require explicit online acknowledgment at apply as well as existing local authorization. No provider writes, installation or implicit credential setup.
5. Amend `contracts/wi3.md`'s raw-file bound, stored/index/disk proof and raw-content reader provisions (including the original 64 KiB statements), `wi3-plan.md`'s content-query/file bound, and `docs/tidy.md`'s retirement limits only for new Git v3 retirement under FR-029–FR-032. User content becomes 16 MiB/file and 64 MiB per full user-content pass, streamed in at most 64 KiB buffers; metadata remains 64 KiB/file, old v2 and jj remain unchanged. The new policy must cover every stored fact, disk open/hash, decoded manifest and deletion-adjacent validation. Current source sites are `retirement_git.go`'s stored-file limit/buffered blob reads and `retirement_manifest.go`'s admission, walker, validator and pre-unlink checks; these are distinct consumers, not one cap. Shared helpers must enforce the selected version/backend policy rather than broaden every caller.
   Git v3 retirement additionally recognizes only the optional exact registration-root `COMMIT_EDITMSG` as inert native metadata. The unchanged 64 KiB metadata cap, two full registration-manifest passes, single operation ledger, complete owner/link/time/hash/EOF proof, aggregate 1,024 entries and encoded 1 MiB bounds apply; this does not grant completion authority or admit nested/lookalike/other unknown paths. Old Git/jj v2 vocabulary, records and unlink semantics remain unchanged; no new wire field, effect, pass, raw process or recovery promise is added.
6. The source sampling audit at the baseline counts three full observations during plan (initial, repeat, locked-store final) and eight during apply (two coordinator preflights, before/after recovery-adapter checks, coordinator after-recovery, coordinator before-removal, and two removal-adapter checks). Each full observation reads stored user files once, disk user files twice, and physical/registration metadata twice each. FR-032 derives its complete-operation budgets from this actual guard graph, including final native-delete checks. Batched raw-object reading prevents 315–358 separate subprocess launches per sample; stream framing/type/OID/length/EOF checks preserve complete proof. The later plan must demonstrate bounded concurrent input/output/stderr handling and cancellation, and test the real-sized fixture under the deadlines. Native Git removal's internal I/O is not mislabeled as instrumented stream bytes. A new direct-file unlink implementation would require a separately budgeted/verified path; none is introduced here.
7. Full streamed disk comparison binds device/inode/type/mode/link/size/mtime/ctime, full digest, exact EOF and the path-to-open-descriptor relationship; same-size actor changes and restored mtime must fail when observable. Existing same-user timestamp-granularity/ABA qualifications remain. A complete sample's bytes cannot be reused to skip a required fresh post-recovery or pre-removal sample.
8. Publish the new action/proof/completion/mapping fields in a new tidy schema/version and corresponding private plan validation. Do not add new enum values to old strict schemas or reinterpret old stored plans. Exact CLI grammar, type shapes and allowed command sequences belong to the separately reviewed plan/contract phase, not assumed here.

## Shared consumers and unchanged boundaries

Creation, reference tidy and both retirement paths consume the shared complete tree safety evidence, so all must receive the same limit amendment and conformance fixtures. Existing inventory can provide qualified observations, but partial listings, a narrow `clean` query, and its helper-neutralizing execution path cannot authorize mutation. All-path physical retirement proof remains required.

Hosting supplies bounded read observations, not deletion authority. Current hosting v1 lacks stable provider IDs and merged/integration-commit fields; the new proof must obtain and validate those facts without silently reinterpreting existing inspection output. A separately reviewed plan will identify any new hosting result contract; its existing v1 fixtures remain intact.

No constitution principle is weakened: evidence precedes local effects, exact ownership is explicit, incomplete proof retains, native backends remain separated and old local functionality needs no network. The expanded provider trust and legacy-completion trust are visible new capabilities requiring independent specification/security review, not inferred exceptions to current contracts.

## Spec 031 amendments

[Spec 031](../031-tidy-integration-proofs/spec.md) amends exactly the following five items of this Spec, documentation only, with no change to any published v1/v2 contract:

1. Patch similarity (spec "Assumptions and scope": similarity is optional supporting information only): Spec 031 makes forge-free patch equivalence a default deletion proof with exact semantics, because local deletion keeps a recovery ref and journal entry (tip commit and history only; not the reflog or `branch.<name>.*` configuration; manual restore; local to the clone) and strictness is reserved for real content loss. Classes: `patch-exact` (verbatim digest), `patch-id` (stw normalized digest tolerating only indentation, trailing whitespace and CR; never git's whitespace-erasing default patch-id; subclass `integrated-modulo-whitespace`, retained as `whitespace-significant-difference` on whitespace-significant paths; binary paths match only exactly; ranges with merge commits are not eligible), `merge-noop` (clean merge into the base yields exactly the base tree, one merge base, no gitlink difference, no merge attribute) and `no-net-change` (branch tree equals merge-base tree, never labelled integrated). Per-commit cherry-pick replay and subject similarity stay unaccepted. FR-010 protections and the online contract are not changed by this item; forge-free proofs never override a protected ref.
2. Read-only planning configuration: the refusal of `core.hooksPath`, `core.fsmonitor` and `submodule.*` becomes neutralization (Spec 031 FR-019..FR-022), the plan succeeds with a note; apply keeps every refusal; `hook.*`, `core.attributesFile`, `includeIf` and the other refusals stay.
3. Collection limits: the whole-output 64 KiB limit for reference and registration collections is replaced by bounded streaming (Spec 031 FR-024..FR-025).
4. Total planning time (FR-032 and FR-025 here: ten-second offline plan, 30-second online plan): the new forge-free proof phase adds its own 60 seconds, per proof command 10 seconds and per tip 20 seconds. Offline plan total is 10 + 60 = 70 seconds; online plan total is 10 + 60 + 30 = 100 seconds with the online phase, its 128-request and 32 MiB budget unchanged; apply stays 60 seconds total and re-evaluates only the proofs of selected deletions inside it. The 10-second per-observation contexts are unchanged.
5. Collection completeness and budget exhaustion (online contract: "a full final page without proven exhaustion refuses"; FR-025: 1,000 records without proven exhaustion is incomplete, "narrow selections are available when a complete plan cannot fit"): positive evidence stays proof (an exact-head merged PR found and passing the full tuple verification and re-reads), and only absence is inconclusive. An incomplete collection no longer refuses the plan: OIDs without a found PR are retained `discovery-incomplete`. When the request budget runs out, the plan also completes instead of requiring a narrower selection: the remaining OIDs, in ascending order, are retained `discovery-budget-exhausted`. Plan request accounting follows the baseline source (2 repository reads, at most 10 pages, 1 read per candidate PR: 116 candidate reads at most; spec FR-018); apply-time `RevalidatePullRequest` reads are outside it.
