# Pre-delivery teardown assessment — incomplete design mechanism

## Authority and existing contract

The actual requested watch outcome is a deadline and backoff. A strict deadline on every process phase, including mandatory teardown and physical delivery, was a proposal in this design/brief, not an independently approved owner policy. D1 migration, D2 poll counts and internal phase allocations are engineering choices. No human decision is requested merely to change those unapproved proposal details.

The existing [hosting guide](../../docs/hosting.md) nevertheless states a 30-second total operation bound, and the [accepted transport contract](../022-bounded-go-gh/contracts/transport.md) retains that overall deadline. Preserve these accepted bounds and Tier 1 behavior: do not add an undisclosed unbounded teardown tail, extend the existing operation to 30s plus arbitrary cleanup, leak workers, or kill the library host. Final-delivery C alone does not supply missing teardown bounds. The source currently uses a context deadline and synchronous cleanup; their actual limitations below must not be represented as a stronger proved wall-clock guarantee.

## Phase arithmetic and counterexample

The previous proposed `W=D−1s` is insufficient even for an otherwise finite cleanup: cancellation at29s + an actual1s WaitDelay +250ms deletion +100ms delivery completes at30.35s. There is no delivery reserve left when WaitDelay alone reaches D.

A concrete **allocation candidate**, not an accepted mechanism, is operation cutoff at27s, teardown completion cutoff at29s and final delivery cutoff at30s. Thus operation≤27s, teardown≤2s and final delivery≤1s, with every cutoff tightened by a shorter parent deadline. Polling deadline/backoff stay explicit, no total limit is raised, and no new work starts during teardown. A normal opposing case (27+1+.25+.1=28.35s) fits. A4s synchronous RemoveAll yields32.1s under the same allocation, proving that larger reserves alone do not create a bound.

The AST/source-only probe at `/tmp/stw-spec030-round3/teardown_test.go` confirms the three actual1s WaitDelay assignments and the two synchronous RemoveAll call sites. It exercises these exact arithmetic cases and finite normal/slow synchronous-cleanup models with an already-cancelled context; every model returns/joins and leaves no worker. It is not evidence that real pending filesystem or Close calls are interruptible.

## Completion/failure protocol required of any candidate

For each owned child, transport/body and temporary root, operation completion must carry one of `not-created`, `completed` or an explicit cleanup failure with residual-state qualification. A cleanup attempt starting or a context becoming done is not `completed`. Before final delivery, the host must know that no child, closer or deletion worker remains active; an error result never permits an abandoned goroutine. Preserve exit1 on failure and never turn a late terminal PR sample into success after the applicable deadline. Failures before a PR sample may have no JSON if safe final delivery is no longer possible.

The current void cleanup closures cannot supply this protocol. A synchronous context-aware wrapper also cannot bound a call already inside RemoveAll or Close. An implementation task promising to discover the mechanism later is not a reviewed design. The mechanism and its failure states must be specified and independently reviewed first.

## Concrete next alternatives for the coordinator

1. **Focused mechanism design within the accepted bounds.** Keep the27/2/1 allocation as a testable candidate and design a narrowly owned watch cleanup mechanism for the exact paths above, without changing legacy one-shot/CI behavior. A fixed self-cleanup subprocess is one possible investigation for owned temporary roots: it would need a private non-forgeable target capability, confined deletion, explicit completion/error/residual state, bounded stop and reaping, and Linux/macOS parity. It would not by itself solve in-process HTTP Close, nested native setup calls or pending filesystem qualification. No generic cleanup command, arbitrary path argument, process-tree framework or runtime change is authorized here. This is not yet a complete or accepted option.
2. **Retain the currently accepted constraints and hold watch implementation.** Preserve lifecycle/compact/v2/expected-head designs and the explicit watch requirement, but do not advertise the five-feature delivery as complete. Reconcile the source-specific pre-delivery mechanism before spending review round3. This is the safe current state, not cancellation of the requested feature.

Changing only the unapproved whole-process proposal can be an ordinary engineering decision, but an undisclosed/unbounded cleanup tail is not an acceptable substitute. A future proposal that actually relaxes the accepted30s operation guarantee or permits residual private data/child lifetime requires explicit scope/risk disposition through the coordinator after a concrete review.
