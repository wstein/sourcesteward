# Authentication ownership: bounded design candidate

**State**: Proposed source-only correction for the same final design gate. Two NOT CLEAR reviews remain counted; round3 is unspent. This selects a watch-owned direct-child lifetime, preserving existing authentication. It does not select token-only watch, introduce a persistent guardian, or claim production/platform acceptance. The component HTTP/private-directory protocols in [watch-lifetime.md](watch-lifetime.md) remain part of this candidate; this document replaces that assessment's rejected direct-child assumption and current-options paragraph.

## Accepted boundary and producer evidence

Existing hosting promises a30s operation bound and supports environment/config/keyring authentication. Keep both. The user's deadline/backoff request did not separately approve an absolute crash-proof process-exit promise. Proposed absolute cutoffs remain W=D−3s, T=D−1s and D=start+30s, tightened by parent deadline; operation, teardown and delivery share this clock. Live parent-context cancellation enters teardown immediately. Abrupt destruction of the owning process, hostile same-user intervention and a kernel that cannot complete kill/wait are outside the existing responsive trusted-substrate contract, not newly supported cancellation modes. Do not claim cleanup after SIGKILL of stw. No background guardian can guarantee cleanup after simultaneous destruction of both processes, and none is added.

Official [gh2.102.0 ActiveToken](https://github.com/cli/cli/blob/v2.102.0/internal/config/config.go) can attempt two keyring Gets; its [keyring wrapper](https://github.com/cli/cli/blob/v2.102.0/internal/keyring/keyring.go) waits up to60s. [go-keyring0.2.8 Darwin Get](https://github.com/zalando/go-keyring/blob/v0.2.8/keyring_darwin.go) starts `/usr/bin/security find-generic-password` with CombinedOutput and no inherited cancellation context. Therefore killing gh first can orphan security. The installed gh module metadata matches those versions; no real token/keychain operation was executed. Linux's corresponding keyring route uses existing caller OS services; those services are not owned children and must never be signalled.

Apple's [security command dispatcher](https://github.com/apple-oss-distributions/Security/blob/main/SecurityTool/macOS/security.c) and [generic-password implementation](https://github.com/apple-oss-distributions/Security/blob/main/SecurityTool/macOS/keychain_find.c) route this command through Security framework APIs. No fork/setsid occurs in the examined command route. That source evidence supports the fixed non-daemonizing producer assumption; it does not prove all transitive framework implementations or arbitrary future executables. This design retains the existing trusted native executable boundary, not arbitrary hostile wrappers. It neither pins a new minimum/exact gh version nor silently substitutes a token-only route. An unexpected process graph is a typed operation failure, not truncation-as-success.

## Ownership and cancellation protocol

The watch-only command host owns each Start/Wait; existing one-shot/CI runners stay unchanged. It starts the qualified native/auth child in a fresh POSIX process group, captures bounded private stdout/stderr, records leader PID, group, parent, owner and birth identity, and keeps the leader **unreaped** until group closure. There is exactly one Wait owner. Do not use CommandContext's automatic direct-child Kill or call Run/Wait concurrently with this protocol: that recreates the orphaning counterexample. No library os.Exit or detached cancellation worker is added.

Normal completion requires a waitable leader, no live fixed-producer descendants, closed/drained owned stdout/stderr and exactly one final Wait. Authentication output is memory-only, capped by the existing16KiB token limits; errors never include token bytes, child arguments or raw stderr. The token can be consumed only after the normal authenticated completion; cancelled/failed ownership never produces another GET.

At W/cancellation: forbid further starts/GETs; while the leader is still pinned, SIGSTOP its owned group. Observe the leader stopped or waitable. A stopped parent cannot reap a child, so an observed child PID plus birth/PPID remains pinned even if that child exits. For each known direct security child, verify same owner/parent/birth under the stopped parent, stop it, then terminate it. Resume gh so its actual CombinedOutput/Wait reaps that child. A second keyring fallback can start; stop/observe/terminate/reap it in the same way. The expected graph has at most two such attempts; cap observation records at32 and the cooperative stop/reap subphase at600ms. This is a work cap, not a claim that every future executable has exactly two children.

If gh has no child while stopped, terminate the leader while its PID/group is pinned. If the cooperative phase cannot finish or gh dies first, use terminal group termination **before** the leader's final Wait. Observe every member returned by the bounded group query as nonexecuting (zombie/waitable), close/drain streams, then reap the owned leader exactly once. Do not signal the numeric group after that reap. A positive Kill return alone is not proof of group closure. Unknown records, partial enumeration or identity disagreement are not empty-group evidence. The final fallback consumes the remainder of the1s child-tail allocation; it cannot reset T.

The examined producer keeps security in the inherited group. The Linux finite model additionally handles a single direct setsid child by discovering it through PPID under the stopped gh parent and pinning its PID before individual signals. That model does not extend the production contract to arbitrary double-fork/daemonization or hidden descendants. Such behavior is an unsupported producer graph, never silently certified contained. If the implementation cannot observe the required fixed graph on a supported platform, the implementation gate stays closed; do not deploy an early token-only refusal as a substitute.

## Platform observation and identity limits

Linux implementation must use bounded complete reads of the stopped leader's task/children observations plus identity records, and complete owned-group observation; the disposable model's global `/proc` scan that ignores unrelated parse errors is **not** a production parser. Every task needed to establish the fixed parent's children must be accounted for; errors/record caps fail closed. Parent-stop/recheck ordering prevents signalling a reused child PID; keeping the leader unreaped prevents PGID reuse. Birth time is an additional check, not a substitute for this pinning.

Darwin design uses bounded native process metadata, the already pinned x/sys KinfoProc layout, and a fixed caller-allocated buffer for `kern.proc.pgrp`; [XNU's sysctl interface](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/sysctl.h) identifies group and parent fields. No SysctlKinfoProcSlice hidden ENOMEM retry, unbounded process-list allocation or guessed Waitid wrapper is permitted. Perform one bounded query per observation, check exact record-size alignment/fullness, same parent/group/owner/birth and stopped/waitable state; cap32 records and poll only until the absolute child cutoff. A full/changed/incomplete buffer is an observation failure, not success. The exact supported Darwin syscall wrapper and states must be verified against its headers and source-only platform conformance before runtime acceptance. No Darwin execution or terminal proof has occurred; Linux proof does not transfer.

A process may become an orphan zombie if gh dies before reaping it. stw is not that orphan's parent and cannot honestly claim its reap. No subreaper installation, privilege change or kill of OS credential services is authorized. Distinguish three observations: **nonexecution established**, **owned direct child reaped**, and **orphan reaping unconfirmed**. Only the first two permit proceeding to final failed delivery; all three being satisfactory is required for ordinary clean success. This is not a requirement that the root cause leave zero OS metadata. An unconfirmed orphan zombie is OS metadata, not an executing worker or secret-bearing open stream.

An inability to establish nonexecution is fundamentally different: the host cannot advertise bounded completion, close its design obligation, arm C over a possibly running worker or pretend an error code makes a leak safe. That case is outside the proven fixed-producer/OS capability. It remains a named acceptance blocker, with no automatically selected policy relaxation. Implementation must demonstrate every supported ordinary error/cancel path reaches either clean completion or the nonexecuting terminal-error state inside T.

## Failure outcomes and private metadata

Use existing v2 error structure, not hypothetical new `boundary.teardown` schema data. A cleanup/ownership error gives status:error, boundary.complete:false, stop:failed and exit1; deadline/cancellation retains its earlier stop/code, while fixed limitation strings carry independent cleanup evidence. Codes are `hosting-auth-cleanup-failed` or `hosting-teardown-failed`; static limitation values are `auth-orphan-reaping-unconfirmed` and `private-metadata-residue-possible` when applicable. They are bounded public classifications, never PID/process text, tokens, filenames, raw errors or authentication paths. One diagnostic remains the maximum; preserve these qualifications even when output-limit handling clears PR/identity samples. A failed output may prevent their delivery, and documentation must say so.

Normal private deletion follows **after** nonexecution, stream closure and owned Wait, using the confined helper described in the component assessment. If orphan reaping alone is unconfirmed, no descendant can still use the private directory, but the overall result stays unsuccessful. A killed/timed-out deletion helper is itself synchronously reaped before C; it leaves at most one0700 root with0600 copied metadata and the residue qualification. No auto-retry, background queue or later native session follows. Retain private permissions, never expose copied contents, and never claim failed cleanup completed. A cleanup helper is a single bounded leaf child, not a guardian: execution≤500ms plus kill/reap≤200ms, no descendants/control service, original T, no renewed clock.

The complete normal/error pipeline is: stop admissions → owned child completion/nonexecution plus direct Wait → abort owned raw HTTP connections and join tracked I/O/dials → confined deletion acknowledgement or explicit private residue → close all owned capabilities → resource-free success/error delivery C. Native/auth and HTTP are mutually exclusive, but reserve1s +250ms +500ms +200ms =1.95s within the2s teardown phase conservatively. Earlier jj session cleanup uses the same caps before another session starts, charged to W. Responsive-OS assumptions are the same as the existing accepted synchronous native/HTTP operations; application-level unbounded callbacks/closers are not excused by them.

## Finite evidence and final gate

`/tmp/stw-spec030-auth-ownership/ownership_test.go` passed on linux/arm64. Normal authentication shape completed~18ms with zero child terminations and an actual parent-Wait marker. Cutoff with two sequential keyring fallbacks completed~62ms with two terminated children, two parent-Wait markers, leader reaped and both streams EOF. A one-hop setsid control completed~58ms with the same acknowledgements. Five ownership predicates reject reaped leader, changed birth, changed parent and unstopped parent. Independent control-pipe EOF was observed while auth stdout stayed open; no guardian is selected, so that component does not imply a parent-death guarantee. Fixture token stays private capture. The earlier direct-parent-kill counterexample remains the RED opposing case. No real credential, provider, installation or production code was touched.

These are finite protocol/ordering evidence, not a hard timing proof, actual gh/security test, complete process parser, abnormal orphan-reaping proof or Darwin acceptance. The next independent review must evaluate this explicit terminal-error distinction and accepted-baseline comparison, all component blocking paths and exact platform gates. If those gates cannot be met without an accepted-contract change, return that concrete conflict to dispatch rather than silently weaken the deadline, authentication support or no-live-worker condition. Round3 must not stamp production capability from these fixtures.
