## Decisive fixed-producer counterexample and scope options

This is not an arbitrary test-injection objection. Official [gh2.102.0 ActiveToken](https://github.com/cli/cli/blob/v2.102.0/internal/config/config.go) first checks environment/config, then encrypted storage. Its [keyring wrapper](https://github.com/cli/cli/blob/v2.102.0/internal/keyring/keyring.go) has a60-second timeout around keyring access. The pinned dependency [go-keyring0.2.8 Darwin Get](https://github.com/zalando/go-keyring/blob/v0.2.8/keyring_darwin.go) executes `/usr/bin/security` through a new exec.Command/CombinedOutput without a parent context. The official gh go.mod and local installed gh build metadata both identify0.2.8. Reaping the direct gh child therefore does not establish completion of all supported authentication descendants.

A finite source-only shape test reproduced the ownership failure: a direct authentication-model child was cancelled and reaped in~65ms (40ms context,20ms WaitDelay), while its independently spawned descendant completed at~174ms; the no-descendant control completed in under1ms. The descendant ended before the test completed; no real keyring/provider was accessed. This scaling demonstrates why an actual1s WaitDelay cannot certify completion of a longer-lived descendant. Neither a larger reserve, private deletion helper, owned TCP close nor final-delivery C controls that process.

**Exact options for the coordinator, not a human permission question:**

1. Preserve full existing gh/keyring authentication for watch and add a narrowly scoped authentication-descendant containment/lifetime design before round3. That is extra process-ownership work beyond the currently proposed direct-child+private-cleanup helper; no generic process-tree framework, privilege or runtime implementation is authorized by this assessment. It must cover Linux/macOS and prove no live auth descendants before private-directory cleanup/final delivery. The current prototype does not supply that mechanism.
2. Consider an explicit **new-watch-only** capability restricted to a host-appropriate existing environment token, with early refusal when absent. Still use bounded `gh auth token` so the existing credential boundary is retained; prove the supported official producer takes the non-keyring route. Legacy one-shot/CI keyring behavior remains unchanged. This is a real new-watch usability/support limitation, not a renamed timeout or an automatically selected policy; it needs a concrete design disposition before schema/tasks claim completion. Plaintext-config and arbitrary future gh-wrapper behavior cannot be silently assumed to have the same proof. No caller setting/token is written or requested by this assessment.
3. Retain the accepted bounds/auth support and hold watch implementation while keeping all five outcomes in scope. Do not claim all-five completion, leave an unbounded auth/cleanup tail, or move an os.Exit into a library. This was the safe predecessor state, not cancellation of watch.

The remaining material comparison is existing supported authentication/owned-descendant behavior versus a new capability restriction or additional contained-process effects. It is **not** whether the owner must approve retreating from the author's previously unapproved stricter deadline wording. No accepted contract is amended here. Further mechanism work should follow one selected bounded direction rather than repeat inventory/proposal loops.

## Call graph and fixed producers

Only explicit watch uses this lifetime: CLI → enhanced PR operation → `inspection.Inspect` → `inspection.Remotes` → one host-selected gh version/token session → up to eight fixed PR GETs → teardown → prepared final delivery C. Local resolution always precedes authentication. Ordinary Git uses fixed inspection/remote built-ins; no arbitrary command, helper or network fetch is added. JJ resolution performs three identity observations and two native remote-list observations, each with a separate serial `withJJSession`; at most one direct native/auth child and one isolated directory are registered by the current operation at a time; **authentication descendants are not thereby owned**, as the counterexample above shows. No session is retained across the next session. After native resolution all jj isolated directories are acknowledged deleted before a gh directory can be created.

The production HTTP producer is the pinned standard Go transport created by SourceSteward, not an arbitrary caller RoundTripper. The production stdout sinks of native/auth children are bounded in-memory captures, not arbitrary blocking Writers. Native metadata opens reject non-regular files/symlinks and use O_NONBLOCK/O_NOFOLLOW on supported platforms, with64KiB read caps. Qualification walks a finite input path/parent chain and Go's finite symlink traversal; watch adds context checks before/after each iteration/call. An arbitrary injected callback that ignores cancellation is not a supported production producer. The watch-only fixture seam must supply the same explicit abort/completion capabilities or refuse before native/auth/network; do not inherit a guarantee from merely implementing RoundTripper/ReadCloser.

As in existing CommandContext/HTTP/native contracts, timing assumes the supported OS schedules the process and completes kernel close/kill/stat/read operations. This is not a hard realtime or failed-kernel guarantee. This candidate does not introduce an application-level unbounded closer/deleter tail under those assumptions. A reviewer must assess this precise baseline comparison: context checks cannot interrupt an in-progress filesystem syscall, and a cleanup child cannot guarantee reaping on a kernel that does not complete Kill/Wait. If those conditions are considered a newly excluded accepted filesystem capability rather than the baseline platform-progress assumption, this candidate is not CLEAR; do not silently claim a stronger bound.

## Explicit adapter and resource state

Add watch-only internal `InspectWithLifetime`/`RemotesWithLifetime` and a hosting factory carrying one per-invocation lifetime value; existing calls retain their current factories. It owns (a) the current child completion, (b) an owned temporary-root registration, (c) request/dial/connection completion and (d) a final teardown outcome. No global registry, filesystem setting or caller-owned transport is changed. All relevant nested native sessions receive the value explicitly; changing only the hosting cleanup closure is insufficient.

Before each root creation register a pending creation state; immediately after successful exclusive MkdirTemp acquire the root and parent directory handles and record canonical parent/leaf, device/inode, current owner and0700 mode. No metadata is copied and no native/auth child starts until registration succeeds. On registration failure stop work with `failed`, `residue_possible:true` and the created private path; never guess a cleanup capability. At most one root is outstanding because cleanup failure stops subsequent work. Callback/defer exits transfer this registration to the same lifetime, never silently call RemoveAll or launch a background deletion.

The state is `not-created` → `active` → `child-reaped/connections-aborted` → `cleanup-running` → `complete` OR `failed/residue-possible`; failures never transition back to active. A root already removed by a successful helper has an explicit acknowledgement; context cancellation or a deletion attempt is not acknowledgement. No native/auth child remains when directory deletion starts. Closing the parent's remaining owned root/parent descriptors completes descriptor ownership even on a cleanup failure; the operation has no continuing worker to hand to final delivery.

## Phases, cutoffs and failure precedence

Keep the accepted30s upper operation budget; do not add a tail after it. `D=min(start+30s,parent deadline)`, `T=max(start,D−1s)`, `W=max(start,D−3s)`: up to27s operation,2s teardown and1s final delivery. Short budgets that cannot leave these reserves refuse before child/auth/network creation. The process host capability preflight is before native effects. Caller cancellation stops new native/auth/GET work immediately and enters the same finite teardown; the original D/T remain absolute and never reset. Only required teardown work may begin after W or cancellation.

At W, at most one serial native/auth child can be pending. Cancel its inherited context; its existing WaitDelay is at most1s. Require Run/Wait completion before advancing; never launch a second child while it is unresolved. Reserve the remaining teardown interval for the owned connection abort/close acknowledgement and one private cleanup helper. Network activity and a native/auth child are mutually exclusive phases; jj cleanup occurs before gh setup. The maximum nominal teardown allocation is1s child tail +250ms connection abort/close +500ms deletion execution +200ms helper kill/reap =1.95s, inside the2s phase. Connection teardown normally has no child tail and native teardown has no HTTP connection; the sum is deliberately conservative.

In the evaluated candidate, a cleanup helper would start only if at least200ms reap reserve remained before T. Its execution deadline is `min(now+500ms,T−200ms)`, WaitDelay at most200ms, no stdout/stderr copy goroutines and no child process of its own. On timeout it is killed and synchronously waited/reaped before delivery. Do not spawn a timeout goroutine around a blocked Wait/Close/RemoveAll. If the fixed OS/producer completion conditions fail, record the unmet design/acceptance condition rather than detach a live worker or early-exit over it.

Earlier native-session cleanup uses the same helper and limits, charged against the original W/T, never a new overall clock. Complete it before the next native session. Any cleanup failure ends sampling immediately. After work returns, cancel all request contexts, abort owned connections, join the owned I/O/dial completions, finish deletion and close the lifetime descriptors before returning prepared delivery. At/after T do not start another cleanup worker, GET, native child or output preparation. Deadline/cancellation wins over terminal PR success; cleanup failure independently prevents success and records private residue even if the first diagnostic remains cancellation/timeout. Exit remains1, never a new code.

## Owned HTTP completion protocol

The watch transport factory wraps only its own standard-library DialContext, tracking each dial until it returns and each resulting raw pollable TCP connection. On stop, an atomic no-new-dial gate is set, all request/dial contexts are cancelled, and every already-owned raw connection gets an immediate read/write deadline and Close before response Body.Close. A late completed dial closes its connection rather than publishing it. No custom production dialer/TLS/alternate protocol or caller-owned connection is accepted by this watch adapter; caller HTTP proxies keep using the existing standard routing and tracked underlying connection. Do not attach credentials to alternate URLs.

Every get and each guard rejection path (error+body, compressed, oversized) routes through the same idempotent abort-then-close owner, including after a fully consumed response. Serialize GETs; track at most the known live dials/connections, and forbid the next GET until the prior body/connection completion is acknowledged. This sacrifices connection reuse, not the fixed GET or authentication contract. CloseIdleConnections runs only after owned raw connections are closed; it cannot be the sole cancellation mechanism. Cancellation/closure errors are redacted typed operation failures.

This is justified by fixed producer mechanics rather than arbitrary ReadCloser behavior: in pinned Go1.27.2, HTTP/1 bodyEOFSignal.Close waits on the transport read loop; that loop observes request cancellation/connection close. The transport's optional post-close drain is at most50ms, and pollable FD.Close evicts blocked I/O before waiting for descriptor closure. The adapter cancels and closes the raw connection first to unblock those paths (also the underlying connection of HTTP/2), then waits for tracked reads/writes/dials to return and closes the body synchronously. No extra closer goroutine can be abandoned. The250ms allowance is a verification target under the stated producer/OS assumptions; source-only net.Pipe evidence supports the unblock ordering, not complete real HTTP/TLS/HTTP2 acceptance. Exact standard transport behavior across supported platforms remains a required implementation conformance test; no live provider request is needed for that test.

## Fixed private cleanup child

A cmd-owned private helper receives **directory capabilities**, not a public path/command option: inherited root/parent descriptors plus a bounded private job carrying the created root's leaf/device/inode. The production mode is an internal process protocol gated by a parent-owned invocation capability; repository/API text cannot select it or create its job. It provides no general deletion CLI. The capability does not grant new OS authority; trusted same-user callers remain trusted as in the existing host configuration model. No library process exits or generic process-tree control is introduced.

The child verifies the root is still the same owned0700 directory and that parent+leaf names that same device/inode without following symlinks. It deletes only fd-relative entries under that descriptor: at most64 entries, depth at most8, O_DIRECTORY/O_NOFOLLOW on descent, unlinking symlinks themselves without following them. It rechecks parent+leaf identity before unlinking the root. These caps exceed the fixed jj metadata-copy layout (at most two64KiB files plus fixed directories/probe) and the normal empty gh neutral directory. Unexpected entries/cap exhaustion/refused identity fail visibly; they do not permit truncation-as-success or arbitrary extra traversal. The native/auth producer has already exited, so it cannot race its own cleanup.

The helper has no provider/network/auth/config access, never reads file contents, never executes another command and has no recursive child cleanup. It exits0 only after all entries and the matching root are removed. Any error, mismatch, execution timeout or killed helper is a failed cleanup; the parent waits/reaps it, closes its own capabilities and reports residue as possible. Kill is a bounded failure mechanism, not an assertion that deletion succeeded. Production implementation must use a qualified trusted executable image/identity for the internal helper and the same supported Linux/macOS fd-relative primitives; no shell, PATH lookup of an untrusted helper or install step is added.

## Residual private metadata and final result

On failure retain0700 root/0600 metadata permissions; do not widen permissions, auto-retry, queue future cleanup or enumerate unrelated temp paths. Residue may include private copied jj configuration metadata and must be reported as such without contents or copied source filenames. Hosting tokens remain memory-only and are never written to the job or temp root. The only exposed path is the generated owned temporary root, never a raw credential/config path.

Historical hypothetical extension (NOT selected; the current design uses existing diagnostics/limitations as specified in [auth-lifetime.md](auth-lifetime.md)): V2 watch `boundary.teardown` would report `status:not-created|complete|failed`, `residue_possible`, and bounded `private_paths` (at most one generated path). Enhanced one-shot uses explicit null because its legacy cleanup does not provide this observation. Watch success requires `complete`; failures preserve earlier PR data only as incomplete evidence. A failed cleanup emits `hosting-teardown-failed` unless timeout/cancellation already has diagnostic precedence; the teardown object still reports residue. No cleanup worker remains active on failure. If output itself fails/expires, a complete residue report cannot be guaranteed; generated roots keep their private permissions and no later worker is silently scheduled. The command documentation must state this writer/process failure limit.

This makes an already possible cleanup-error residue explicit and unsuccessful instead of ignoring RemoveAll errors. It does not change old schemas, legacy cleanup, target repository effects or credential configuration.
