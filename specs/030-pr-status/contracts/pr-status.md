# PR status contract candidate

## CLI and compatibility decision

Existing selectors and NUMBER/PATH rules stay. Add PR-only `--compact`, `--expect-head SHA`, `--watch` and `--json-version 1|2` (default 1). No timeout/interval/retry-count tuning flags in this slice. Explicit `--json-version` requires `--json`; compact conflicts with JSON. Watch/expect with JSON require version 2; invalid combinations and SHA syntax (including an explicitly empty expected head) exit 2 before native/auth/network, with no JSON. `repo`/`ci` reject these new flags. Both entry points share parsing, operation and rendering.

Ordinary `--json` retains the old v1 operation/validation and bytes; v1 schema and fixtures remain unchanged. Enhanced human mode and explicit v2 use the new result/decoder. This deliberate legacy-format path preserves existing v1 behavior, including its stricter existing requirement for non-null head repository. There is no v1 projection that silently loses mismatch/watch metadata. Detailed human output preserves existing sections; new labelled evidence is appended. The v2 decoder permits `head.repo:null` as explicit unavailable identity; it cannot establish continuity across a later change to/from null. CI retains its existing reader and resample behavior. The new format is an explicit migration, not a default v1 schema-version change.

Evidence correction: at the inspected base v1 is **extensible**, not strict: `hosting.schema.json` has no additional-properties prohibition and `TestHostingSchemaOfflineFixturesAndInvariants` accepts `future:true`. v2 is proposed because newly required nullable fields, lifecycle invariants and watch outcomes warrant a distinct guaranteed contract, not because extra v1 properties currently fail validation. v2 consumers ignore unknown properties and reject unsupported `schema_version`; adding optional properties preserves v2, removing/renaming/changing required semantics requires a new version. No old schema is tightened.

## Field and state table

One fixed `GET repos/OWNER/NAME/pulls/NUMBER` supplies all remote fields. Validate UTF-8/JSON, number/base repository, existing title/URL/draft/head/base SHA/ref evidence with the current hosting grammar (nonempty refs and valid full repository names); response URLs are display-only. Unknown API fields are ignored. For new required nullable fields distinguish an absent member from explicit null using raw JSON presence checks, not pointer zero values. Dates are RFC3339 timestamps when strings; preserve valid API timestamp text. Non-null SHA values use exactly 40 lowercase hex.

| REST evidence | Required interpretation |
| --- | --- |
| `merged` absent/null/non-bool; unknown/missing/non-string state; missing new nullable member | Error `hosting-pr-evidence`; no new sample accepted |
| `state:open`, `merged:false`, `closed_at:null`, `merged_at:null` | `lifecycle:open`; raw `merge_commit_sha` may be null/test SHA; `result_sha:null` |
| `state:closed`, `merged:false`, `closed_at:date`, `merged_at:null` | `lifecycle:closed-unmerged`; raw SHA may be null/test SHA; `result_sha:null` |
| `state:closed`, `merged:true`, `closed_at:date`, `merged_at:date` | `lifecycle:merged`; `result_sha` equals raw `merge_commit_sha`, including null |
| Any other state/bool/date combination, invalid date/SHA or wrong nullable type | Error `hosting-pr-evidence`; never normalize to a guessed lifecycle |
| `merge_commit_sha:null` on an otherwise merged record | Valid merge observation, result unavailable; do not invent a SHA or make another endpoint call |
| `mergeable:null/true/false`, absent or otherwise changed | Ignored by this capability; no mergeability claim, no retry trigger |

Output PR object preserves the old field names, adds `merged`, `merged_at`, `closed_at`, `merge_commit_sha`, `result_sha`, `lifecycle`; `head_repository` may explicitly be null. `merge_commit_sha` means GitHub's raw reported value. Before merge it may be a test-merge SHA; after merge it depends on merge method. A rebase result names the base-updated commit, not necessarily the observed/reviewed head or the base's current tip. Dates are API reports, not independently verified historical proof. No merge method, review attestation, reachability or current integration-tip proof is inferred.

The standalone schema embeds unchanged copies of the existing git_identity, jj_identity, repository, candidate and diagnostic definitions under local $defs; it has no external references or loader dependency. PR refs must be nonempty; each non-null PR repository name has two 1–100 character segments matching `[A-Za-z0-9_][A-Za-z0-9_.-]*`, exactly the existing hosting validRepo grammar. The envelope is PR-only schema_version 2, with backend/identity/repository/candidates from existing hosting resolution; no CI arrays. `observed_at` is UTC final result assembly time, not successful delivery time. `sampled_at` is UTC completion time of the last fully validated PR response or null. `pull_request` holds that last sample, or null. `observation.samples` counts fully validated samples; `boundary.requests` counts attempted fixed PR GET invocations, including a failed GET, never authentication or native commands. `initial_head_sha` is the first valid sample head or null. `expected_head` is input or null; expectation is `not-requested`, `unobserved`, `matched` or `mismatched` against the last valid sample. An error can retain a last sample with earlier sampled_at; `status:error` and `boundary.complete:false` forbid treating it as a fresh terminal success. No timeline is retained. Schema conditionals reject successful identity_changed/mismatched expectations, enforce expected-head null relationships, backend/identity agreement, raw/result SHA null coherence, positive request counts on success, request/sample upper bounds and null PR/sample timestamp agreement. The output-limit exception may retain historical samples/requests while the PR/identity/timestamp/initial-head fields are cleared; it does not retain a sample timestamp without a sample. Arbitrary non-null SHA equality and counter provenance still require operation tests.

## Sampling, terminal and exit rules

For enhanced one-shot: resolve/auth once, make exactly one GET, validate, apply expectation, finalize/render once. An open sample succeeds. Watch: resolve/auth once; first sample establishes continuity. On every later sample compare `head_sha`, `head_ref`, `head_repository`, `base_ref`, `base_repository` to the first sample. Any difference sets `identity_changed:true` and terminates `changed`, even if the head is the same. `base_sha`, draft, title and lifecycle may change and are reported from the latest sample. An observed A→B terminates at B; it cannot later recover at A. An A→B→A change entirely between requests is undetectable; there is no transactional or exhaustive history guarantee.

After a fully validated sample and a live context: apply mismatch first, then observed identity change, then terminal lifecycle, then one-shot success, then budget. Thus a merged sample with unexpected head is not success. For a watch with no expected head, a changed-head merged sample is also not success. Field/HTTP failure stops before these predicates; it never creates a sample. Deadline/cancellation observed before finalization overrides success. A cancellation during delivery changes process outcome to failure even if already serialized JSON says ok; consumers must check exit and complete JSON as with existing writer failures.

| Stop (`observation.stop`) | Status / exit | Diagnostic |
| --- | --- | --- |
| `sampled` (once), `merged` or `closed-unmerged` (watch) | ok / 0 after complete delivery | none |
| `expectation-mismatch` | error / 1 | `hosting-head-mismatch` |
| `changed` | error / 1 | `hosting-pr-changed` |
| `request-limit`, `timeout`, `canceled` | error / 1 | `hosting-watch-limit`, `hosting-watch-timeout` (watch timeout; once uses existing `hosting-canceled`), `hosting-canceled` respectively |
| `failed` | error / 1 | existing native/selection/auth diagnostics, `hosting-pr-failed` for HTTP/transport, or `hosting-pr-evidence` for malformed evidence |
| `output-limit`, `output-unbounded` | error / 1 when safely deliverable | `hosting-output-limit`, `hosting-output-unbounded` |
| Invalid invocation | no observation / 2 | usage diagnostic only |
| Deadline/cancellation/write failure during delivery | process 1; possibly partial/no JSON | no unsafe second write; bounded diagnostic if still possible |

A 401/403/404/429, redirect, compression, malformed/oversized body or transport failure terminates immediately; no retry, `Retry-After` sleep, synthetic closed state or guessed merged flag. Retain a prior valid sample as incomplete evidence. Use existing safe generic messages, never API bodies/token/URL credentials. `boundary.network` is set when the first guarded GET is invoked; early sink/native/auth failure is false.

## Watch algorithm and bounds

Proposed constants: one 30-second operation budget, at most 8 numbered PR GET invocations, 1 MiB raw body, normalized body and final encoded result (each, not combined); auth stdout/stderr 16 KiB each; existing native sublimits remain tighter. No collection or pagination is introduced. One-shot enhanced PR has max_requests 1; watch 8. Parent deadline always tightens the budget. No existing Tier 1 bound is raised.

For watch, `D=min(start+30s,parent deadline)` remains the proposed overall ceiling, tightened by parent cancellation. **Round2 invalidated the prior `W=D−1s` work cutoff**: a current one-second WaitDelay alone consumes its entire delivery reserve. The replacement allocation candidate is `W=max(start,D−3s)`, teardown cutoff `T=max(start,D−1s)`, then final delivery until D: at most27s work,2s teardown and1s delivery for the ordinary30s budget. Native/auth/GET contexts use W; required teardown must have its own designed bounded completion/failure protocol before T; final delivery C retains D. A short parent budget can refuse before native/auth/read rather than launch work with no teardown reserve. [The source-specific assessment](../teardown-assessment.md) shows why this allocation alone is NOT a cleanup bound; the current scoped mechanism is in [authentication ownership](../auth-lifetime.md). Independent design review and implementation acceptance remain required. Enhanced one-shot retains its existing operation/writer contract. No larger overall bound, per-poll reset or silent unbounded cleanup tail is selected.

First GET is immediate after resolution/auth. Before each GET check parent cancellation, now<W and request count<cap, then increment count and invoke only the typed fixed endpoint. Check the work context again after every GET/decode before accepting a sample. Between valid open samples wait cancellably 1s, 2s, then 4s for every remaining interval; no jitter or hidden retries. Never shorten a wait to squeeze another poll before W. If the full next wait cannot finish before W, wait only until W, then finalize timeout; do not make another request. Budget applies to errors as well. After request 8, process its valid terminal/mismatch/change outcome before declaring request-limit for an open sample. Zero successful samples is permitted on failure.

Buffer the complete final representation under 1 MiB including newline before any stdout write. Oversize drops identity/candidates/repository/PR and clears sampled_at/initial_head/expectation to unobserved as applicable; samples/requests counters remain historical, stop becomes output-limit and a fixed small error envelope replaces the large output. Bound human escaping expansion by the same cap. No intermediate progress, sleeps, sample arrays or JSON stream. Rendering/encoding after W must still finish before D; if they consume the reserve, return failure without starting output. Scheduling/OS failure can prevent a well-formed result; hard realtime scheduling is not claimed.

## Delivery decision

**Proposed preferred option C — command-owned final-delivery guard.** This is a reviewed alternative under assessment, not implemented runtime behavior. It retains ordinary stdout/file usability without excluding blocked delivery from the original deadline. A command-owned guard may terminate only its own executable process with exit 1 during final delivery, after every native operation, authentication process, HTTP body/connection session, subprocess Wait, temporary-directory cleanup and operation-level defer has completed. No library may call os.Exit. Neither the guard nor a timer may kill the process while any such cleanup remains pending.

The process host establishes the original monotonic D before work. The work context W is D−3s with teardown cutoff T=D−1s, tightened by parent cancellation; successful operation return alone is insufficient: the host must receive a resource-free prepared-delivery result **after** all cleanup. No operation callback, auth close, pending child, target mutation, borrowed lock or cleanup defer may remain reachable from the delivery closure. Final formatting/JSON encoding, bounded stdout writes and root stderr diagnostics occur only in this resource-free phase. A pre-output error uses the same final-delivery path, so an HTTP/native error cannot escape through the old unguarded report function. The guard retains D, never `now+remainingBudget` or a renewed 30s clock.

Command-host capability is checked before native/auth/network. Both cmd/stw and cmd/gh-jj must install the same guard-capable prepared-delivery protocol. A library call without that host protocol refuses watch with hosting-output-unbounded before any effects; a library never inherits permission to exit its embedding process. Legacy one-shot entry points and their writer-failure behavior remain unchanged. Any usage error still exits 2 without a PR observation; no watch operation or delivery guard has started. A selected watch operation's operational or delivery failure stays exit 1; it never introduces a new status code.

**Final exit arbitration:** one command-owned final arbiter monitors the original parent cancellation/deadline from arming until process exit. The delivery thread writes synchronously; no detached writer goroutine is used. On timeout/cancellation the arbiter calls process exit 1 directly, without attempting one last diagnostic. On normal completion, stdout and all root diagnostics complete first, then a single candidate exit code is submitted to the arbiter. The arbiter rechecks cancellation and `now>=D` after accepting completion; either failure wins over candidate success. It then performs the sole final process exit immediately. There is no disarm/join interval followed by more rendering, diagnostics, cleanup or delayed exit. A failure already selected is never promoted to success.

A literal production join of a goroutine that calls os.Exit is not possible: successful process exit terminates all its threads. The finite arbiter's timer/signal registrations are deliberately process-lifetime resources, reclaimed by exit; no external cleanup is delegated to process termination. For returning library/test adapters, an injected terminal callback must return, the monitor must stop/drain its timer and join, and those adapters do not claim process-level interruption of arbitrary sinks. Do not advertise a join-before-exit design as covering a cancellation after disarm. A cancellation concurrent with completion is rechecked at the arbiter's final exit decision; no code can atomically sample a clock/context and perform the OS exit syscall. This final nonblocking decision is the linearization point, with no further application work; OS scheduling/failure and signals arriving after it are not hard realtime guarantees. Strong review must assess this boundary rather than accept a hidden race gap.

If D/cancellation is already reached before arming, complete required cleanup, begin no output, and exit 1 through the same final arbiter. **This ordering by itself does not prove the inclusive deadline:** native/auth/child/cleanup paths must actually finish within their inherited work bounds plus the internal reserve. A blocked or unexpectedly late cleanup cannot be made safe by os.Exit. Until the actual finite cancellation and cleanup paths are audited/tested, option C remains behind an implementation gate. No guard at D is permitted to bypass a still-live child or unfinished cleanup merely to make a timing test pass.

Disposable Go1.27.2/linux/arm64 model evidence: actual child Wait and a cleanup-complete sentinel precede guard arming; blocked stdout, stderr and root-error stderr exit 1 around 151–155ms on an original 150ms timer; cancellation exits 1 around 66ms; ordinary temporary file and /dev/null complete exit 0. Five final-decision boundary cases and 100 simultaneous-ready cancellation/completion models pass with one terminal callback and monitor join. An intentionally expired-before-arming fixture exits only after cleanup (~22ms despite a 10ms budget): it demonstrates the safety ordering and exposes the need for real bounded-cleanup proof, **not** successful enforcement of that shorter deadline. This is test-only model evidence; real prepared-delivery entry wiring, all operation cleanup paths, terminal/macOS behavior and completion/cancellation races in production remain unverified.

**Compared alternatives:** A accepts only already deadline-capable stdout/stderr and joins its monitor without exiting a host process, but measured inherited captured stdout, regular files and /dev/null reject SetWriteDeadline (owned os.Pipe works; no terminal available), so it fails ordinary CLI watch usability. B explicitly excludes blocked physical delivery from the bound and would require a contract-relaxation decision; it is not selected. C preserves ordinary sinks and the requested inclusive intent through a narrowly scoped final process boundary, with added cleanup/entry/race/platform verification obligations. C is now the concrete engineering proposal for the same independent review. Do not mark watch implemented/CLEAR while those obligations are unresolved; do not silently choose B or add a library os.Exit.
